# PRP：采购看板统一同步

状态：Approved for implementation。负责人 2026-10-27 在本文提交后明确要求当前分支开发、不得影响其他业务；生产操作未授权。
日期：2026-10-27。
主执行角色：后端工程师。前端范围仅限现有同步任务管理页面的采购入口。

## 1. Goal / Why

一个“采购看板同步”入口、一套配置、一条完整流水线，支持立即同步和每三小时自动同步。只有采购看板发布成功才报告整体成功。

用户已明确授权在当前 develop 分支修改，不新建分支/worktree；没有授权提交、推送、部署、真实采集或生产数据库操作。此前采购 PRP 的手动采集能力不等于本次自动编排已获 PRP 批准。

## 2. Initial feature / Business rules

- 保留 purchasePlanList、purchaseOrderList、purchaseReceiptOrderList 的契约、handler、parser、来源表及历史日志。
- 三个接口变成统一任务的内部阶段；普通任务列表不再显示三个独立操作入口。
- 原有成功来源、历史运行和审计不可删除。统一任务上线后禁止三个内部任务独立定时，避免重复采集。
- 默认调度表达式为 UTC `0 */3 * * *`，表示固定每三小时整点运行，不是从点击开启起倒计时三小时。Asia/Taipei 对应 02:00、05:00、08:00、11:00、14:00、17:00、20:00、23:00。
- 注册时默认关闭真实自动运行；配置页面开启后生效。生产开关启用属于另行授权的上线操作。
- 沿用采购更新时间维度；不改变到货、交期、金额、ItemID 和负责人业务口径。

## 3. Scope

包含：integration_sync 内统一编排、配置与调度、采购内部阶段及失败记录、现有任务页面单入口、配套测试/API文档/SOP/registry/handoff。

不包含：新后台、新导航、第二套任务系统、删除三个采集器、领星写接口、采购规则修改、自动刷新其他业务模块、生产部署/迁移/真实同步、修改 .env 或密钥、提交推送。

## 4. Data source decision

复用 `docs/data-sources/decisions/pmc-purchase-board-decision.md`，状态 READY_FOR_PRP，无未解决 NEED_OWNER_DECISION；结论 REBUILD_SYNC。

数据源和分层不变：领星采购三接口 → RAW/ODS → DWD → DWS；DWS 使用成功来源收货数据及已有店铺、Listing、产品资料、采购规则和人工覆盖。旧系统不参与。

遵循 `docs/data-sources/database-layering-standard.md` 和 `docs/data-sources/field-standardization-standard.md`。源采集时间与看板计算时间分别记录；不把旧主数据标为本次已采集。

## 5. Navigation / Permissions / UI

复用现有数据中心同步任务管理页面和 PageShell 帮助入口。一个账号对应一条采购看板同步配置；多账号必须按现有 source_account scope 隔离，不能合并为跨账号全局权限。

复用现有同步查看、运行、配置和重试 permissionKey，实施时核对实际后端依赖及 IAM 映射，不新增角色判断或放宽权限。

页面显示采购看板同步、自动开关、三小时频率、下次运行、上次整体状态，操作为立即同步、配置、日志。日志展开显示三次采集、DWD 发布、DWS 刷新及失败阶段。保留历史子任务日志可追溯入口。

组件复用：SyncTaskPage、SyncTaskTable、SyncTaskConfigDrawer、SyncTaskLogDrawer、现有操作守卫和 API client；增加三小时频率选项，不改变其他任务行为。

## 6. API / Execution contract

复用现有 `/api/integrations/sync-configs/{id}/run`、配置 PATCH、运行日志与 retry API；手动和自动进入同一编排函数，统一信封、request_id、服务端权限校验不变。

以采购业务级配置作为唯一调度权威。内部来源接口继续保留原始 interface_key 和来源血缘；统一编排不得伪装成某个领星 HTTP 接口对外发请求。具体登记方式优先使用现有治理表，不预设需要新增业务表；若必须新增表，先补充本 PRP 的模型和 Alembic 方案。

顺序：运行前校验 → 计划采集 → 采购单采集 → 收货采集 → DWD 发布 → DWS 刷新 → 整体成功。

- 按账号对整条流程互斥，覆盖手动、定时、重试；内部采集兼容现有限流。
- 每个子步骤有独立幂等键并关联父运行；不得跨接口复用同一个幂等键。
- 首次无水位时，沿用已存在 runner 的历史起点 2026-08-01，按不超过 90 天的日期窗口分段；更早历史不在本任务范围。
- 增量按上次完整成功窗口结束日回叠一天，结束日为本次采购来源日期；日期时区按采购既有契约核对，不套用 Walmart 业务日。
- 水位只在整条流水线成功后推进；失败窗口可以安全重跑。成功来源可保留，部分失败不得发布混合的新看板。
- DWS 刷新沿用事务回滚；失败保留上一版看板。DWD 与 DWS 现有处理器分别提交，不能声称整个流程为单一数据库事务。
- 无新增来源也执行看板日期重算，更新逾期等指标。
- 重试必须保留原窗口及父运行关联，恢复失败处理；采集器原手动限制仅对受控内部编排调整，不能全局取消环境与治理门禁。
- 产品/Listing/店铺仍由既有任务维护；本流程检查依赖和记录来源时效，不隐式触发跨模块同步。

## 7. Implementation plan

1. PRP 确认后，核查目录规则、任务登记及现有模型、权限、执行租约和测试；维护本任务计划文件。
2. 接入业务级配置和三小时调度，明确旧子任务调度的停用/回滚方案；任何实际数据库转换均不在本轮执行。
3. 实现共用编排与时间窗口、水位、互斥、错误记录、重试，并复用三个采集器、PmcPurchaseDwdPublisher、PmcPurchaseDwsRefresher。
4. 前端合并入口、补频率选项及阶段日志，保留历史记录查询。
5. 更新接口说明、SOP、数据接口登记和 CODEX_HANDOFF，完成离线验证。

第三方用法按仓库安装版本查询 Context7 或官方 Celery/React/Ant Design 文档。无新高风险 Skill，无子代理要求。

## 8. Tests / Acceptance

- pytest：手动及 schedule 使用同一完整流程；窗口分段/重叠；三小时 next_run；子步骤失败阻断发布；重复触发互斥；重试及水位不提前推进；账号权限；无新增数据仍重算；旧接口契约回归。
- Vitest：采购仅一行、三小时配置、立即运行、禁用态、阶段日志、其他业务任务保持原行为。
- Playwright：mock API 验证单入口、三小时配置、手动运行和失败日志，不使用真实凭据、数据库或领星 API。
- 运行适用的 TypeScript、ESLint 和后端检查；测试只能使用隔离测试资源，不能连真实生产库。
- 验收必须区分离线实现完成和生产启用完成。后者本轮不执行。

## 9. Rollout / Rollback / Risks

生产上线另行批准：检查代码与迁移版本、既有主数据/规则、Redis/Celery worker/beat、领星治理配置；备份原调度配置；关闭子任务独立调度；完成一次统一同步并核验来源与 DWS；最后开启三小时自动调度。

回滚先关闭统一调度、等待或安全终止运行，回退代码和配置；不删除采购来源/审计，不自动恢复三项定时（旧执行器本来仅支持手动）。必要时走已有受控手动采集及 DWD/DWS 刷新流程，真实执行需授权。

主要风险：旧子任务重复运行、单接口成功被误报为整链成功、窗口/时区漏数、多账号混用、DWD 成功而 DWS 失败、依赖主数据过期。上述均需有测试或明确的上线核验。
