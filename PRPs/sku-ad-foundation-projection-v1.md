# 0100 data projection V1 (code only)

Scope: approved SKU and ad storage, ProductList development time, candidate Listing ad state. No migration-number changes. No existing sync handler, fact writer, scheduler, API, permission, page, or legacy table changes. This adds callable services and tests; it does not turn on any jobs. Main checked at dac75a603b9dffe03f1c764d0413d81a94d3f32d. Local 0100 model SHA must match the installed source.

## Source contract and ownership
- SKU: successful `productList` / `batchGetProductInfo` run, verified RAW request ref, same account, SKU membership and stable identity. ProductList ordinal verified; batch actual response ordinal resolved by ID, not request order. Single page bounded to 1000 items. `publish_sku_raw_page` validates entire membership before projection. Caller owns transaction, must rollback on error. Changes use independent current pointer, snapshot hash and separate extension-only advisory lock. Late observations do not overwrite current. Repeated identical current payload does not create another snapshot. Development timestamp only ProductList `create_time` in Unix seconds, normalized UTC. `read_development_dates` reads a bounded batch of stable identities in the caller's authorized account. UI timezone remains an open presentation choice. All source JSON is redacted using existing helper; values unrepresentable in typed columns remain in payload, not rounded or fabricated. Missing unknown keys remain in raw JSON.
- Ad: one retained RAW blob with correct retention policy. `publish_ad_raw_blob_config` saves observations only, uses existing advertiser/account catalog and rejects ambiguous account ownership; it does NOT confirm store mapping or claim a complete inventory of ads. Incomplete ad identities remain in existing RAW, counted as skipped. `publish_ad_daily_extension` is callable only with an exact fact row and date/hash selected by the existing deduplicating writer, plus trusted blob/ordinal context. No inferred date from RAW receipt. It verifies existing fact identity/currency and writes only extension data. It does not independently replace or prune daily rows; the eventual writer integration must perform same-day replacement and extension cleanup in a governed path. No financial metric authority moves. Historical date/RAW lineage must be verified before daily replay.
- Listing status: `evaluate_listing_ad_status` is a candidate rule, not a scheduled or persisted projection. Requires caller-verified account-to-store association, scoped fresh observations and verified coverage, with explicit freshness window. An empty or incomplete report cannot be treated as disabled. No spend-based inference. Status enumerations and actual report coverage need production evidence before activating rule. Existing Listing status, price and other fields remain unchanged.
