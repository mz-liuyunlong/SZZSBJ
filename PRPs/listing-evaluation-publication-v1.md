# PRP 草案：Listing 评级与生命周期正式生效

- 状态：**BLOCKED_BY_OWNER_DECISION / 未批准 / 不得实现正式写回**
- 关联：PR #277、LM-001–025、LM-059–068
- 数据源决策：`docs/data-sources/decisions/listing-evaluation-preview-decision.md`
- 证据清单：`docs/data-sources/listing-evaluation-evidence-inventory-pr277.md`
- 本文件只把已确认口径和未解决门禁列为可审查对象，不批准生产调度、迁移或历史回填。

## 1. Goal / Why

在可信销售、费用、库存和历史事件证据齐备时，使 WFS Listing 的评级与生命周期自动生效，并保留人工调整优先权、版本、审计和可恢复记录。当前诊断快照继续保持未发布，不能直接当作正式结果。

## 2. Scope

### 已确认的业务边界

- 本轮只计算 WFS；FBM 仍可浏览，但不产生评级或生命周期候选。
- 评级使用「每日销售」已计算的多日销售额与利润，以洛杉矶业务日 T-2 为截止日。广告费与退款不由评级模块再次单独聚合。
- 广告完整性信号以领星广告报表接口已入库的同账号、同 LA 业务日**全部行**为准：整批广告费全零或缺失才阻断，不要求当前 SKU 有广告费，SEM 不能代替广告报表信号。每日销售当日缺数据、成本不完整或缺少次日 00:00 后的最终同步成功证据时，该日也不得支持正式评级。缺失记录不能被当作零销量。
- 人工生命周期调整优先于自动计算；历史阶段没有带时间的权威记录时，不倒推或批量回填。
- 负责人期望证据齐全后自动生效，并可配置执行时间。配置变更只影响将来计算，不覆盖历史规则版本和结果。

### 不在本 PRP 自动授权的操作

- 生产启用调度、历史等级或生命周期回填、外部 API 查询、旧系统修改、正式财务结果改写。
- C/D 跟进、逾期提醒、人工覆盖入口的实现。它们须在数据源与权限方案获批后按独立切片交付。

## 3. Navigation / Page

- 复用「产品 → Listing 管理」现有页面、诊断与规则配置入口，不新增第二套后台。
- 当前页面状态为 `building`；正式等级和生命周期在发布门禁完成前继续显示待确认。
- 保留 PageShell 帮助入口；正式发布后的 SOP 与 API 文档必须在功能标记 `ready` 前完成。

## 4. Permissions

- 页面读取沿用 `page:products:listing-management:view` 与现有账号数据作用域。
- 人工生命周期调整、正式发布、规则管理和回滚必须使用各自的动作 `permissionKey`，由后端校验，不按角色名称写死。
- 人工调整和正式发布属于高风险写入：要求操作者、原因、旧值、新值、规则版本、业务截止日、审计记录与可恢复路径。最终权限键、二次确认及是否需要审批，待负责人和项目权限规则确认。

## 5. Data Source

- 决策状态仍为 `BLOCKED_BY_OWNER_DECISION`，含 `NEED_OWNER_DECISION`；本草案不得进入接口或写入实现。
- 每日销售 MART、WFS 日库存事实与现有监控成功观察只能提供各自已明确的日期和业务键证据；缺失日保持未知。
- 当前归档状态表不具备完整的历史事件回放能力，不得用当前值伪造历史阶段。
- 规则版本、诊断运行与未发布快照属于新系统自有数据；正式发布历史、人工覆盖历史及回滚契约尚未批准。
- 不读取或修改 `old-system/**`，不在正式接口中实时调用外部平台。

## 6. 尚待负责人确认的硬门禁

1. 历史阶段已确认不倒推：先只读核实首次阶段、清货、断货恢复、归档／恢复是否有可回放的时间序列；缺失的旧事件保持未知，从获批上线后的新事件开始留痕。新事件的写入归属和证据契约仍需批准。
2. WFS 日库存和零销量的完整采集水位：如何证明某个业务日是完整观察而非漏抓；缺水位时必须阻断。
3. 正式自动写回的权限、人工覆盖冲突优先级、审计、冻结版本与回滚契约。
4. 可配置调度时间的权限、时区、失败重试、并发与补跑边界；生产启用必须另获授权。
5. 账号、店铺、Item ID、可空 MSKU 的稳定关联、币种及跨账号隔离在正式发布前通过隔离 PostgreSQL 验收。

## 7. API / UI Contract

- 当前诊断 API 和未发布快照保持现状；不把 `candidate_only` 或 `blocked` 暴露为正式生效。
- 正式写入、人工调整、运行历史和回滚 API 的路径、schema、`response_model`、错误码、`request_id`、数据作用域及审计契约在数据源决策转为 `READY_FOR_PRP` 后单独批准。
- 页面不得以模拟等级、静态流程或前端本地状态伪装成正式发布。

## 8. Implementation slices（全部待批准）

1. 完整性证明：账号业务日销售完成事件、成本与广告费、WFS 观察水位，缺证据返回稳定错误码。
2. 人工生命周期调整：权限、原因、时间、审计及自动计算覆盖保护。
3. 正式版本化发布：每个 Listing 的冻结输入、规则版本、结果、发布人或系统身份、事务原子性与回滚。
4. 可配置自动调度、失败重试和逐 Listing 错误；独立验证 C/D 跟进和提醒后再启用。

各切片须能独立测试和回退；不能通过批准本草案一次性启用全部生产功能。

## 9. Validation / Acceptance

- 隔离 PostgreSQL 验证：无水位、零广告费、缺成本、缺库存、跨账号、历史归档、人工覆盖冲突均不得错误发布。
- 同一事实和规则重复计算幂等；输入变化有新快照，不原位覆盖历史。
- 正式发布失败必须事务回滚；诊断快照仍可查询，但页面不得显示为正式等级。
- 全量后端、前端、权限、迁移及 Playwright 测试通过；补齐 API 文档、SOP、帮助入口与交接。

## 10. Rollback / Safety

- 规则及正式结果使用不可变版本和审计记录；恢复须有获批的业务动作，不手写生产 SQL 或盲目迁移降级。
- 本草案不连接生产库、不执行迁移、不启用 Celery、不调用外部 API、不修改 `.env` 或 `old-system/**`。

## 11. 审批状态

负责人已确认 WFS、每日销售 T-2、广告费完整性、人工优先和自动生效方向；第 6 节仍需数据源和权限决定。仅当源决策改为 `READY_FOR_PRP` 且本 PRP 获负责人明确批准后，才可开始正式写回实现。生产调度与迁移仍需独立授权。
