# 组织架构与数据权限规则

## 1. 为什么需要组织架构

运营系统中常见场景：

```text
普通运营只看自己的产品
小组长看自己和组员的产品
主管看整个部门的产品
老板看全部
临时账号看指定 SKU / 店铺
```

这不能只靠角色完成，必须加入组织架构、产品负责人归属和页面数据权限。

## 2. 三者分离

```text
角色 = 能做什么
组织架构 = 属于哪个组、管谁
数据权限 = 在某个页面能看哪些数据
产品负责人归属 = 哪些产品 / SKU 归谁负责
```

## 3. 数据权限模式

```text
all              全部数据
own              仅自己负责的数据
direct_reports   自己 + 直属下级的数据
team             当前小组数据
org_tree         当前组织及所有下级组织数据
selected         指定店铺 / 指定负责人 / 指定 SKU
custom           自定义组合
none             无数据
```

## 4. 页面可单独配置

同一个用户在不同页面可以有不同数据范围：

| 页面 | 数据权限口径 |
|---|---|
| 产品管理 | 主运营 / SKU |
| 每日销售 | 主运营 / 店铺 / SKU |
| 广告总览 | 广告负责人 / 店铺 / SKU |
| 采购计划 | 采购负责人 / 供应商 / SKU |
| 库存预警 | PMC 负责人 / SKU / 仓库 |
| 利润中心 | 财务授权 / 店铺 / SKU |
| API文档 | 系统权限，不走产品范围 |
| 用户管理 | 系统权限，不走产品范围 |

## 5. 产品负责人类型

`core_product_owner.owner_type` 建议支持：

```text
main_owner        主运营
ads_owner         广告负责人
purchase_owner    采购负责人
pmc_owner         库存负责人
assistant_owner   协助负责人
```

必须支持：

```text
start_date
end_date
is_active
```

用于处理产品转负责人和历史归属。

## 6. 负责人历史口径

默认：

```text
权限过滤：当前有效负责人
绩效 / 奖金 / 历史复盘：历史负责人
运营看板：可支持当前负责人 / 历史负责人切换
```

## 7. 后端过滤原则

数据权限必须由后端强制执行。禁止让前端通过参数决定是否看自己的数据。

错误：

```text
?only_my_products=true
```

正确：

```text
后端根据当前用户、当前页面、当前数据权限自动添加 WHERE 条件。
```

## 8. 页面展示

`PageShell` 顶部应显示当前数据范围，例如：

```text
数据范围：仅自己负责的产品
数据范围：自己 + 直属组员
数据范围：全部数据
```
