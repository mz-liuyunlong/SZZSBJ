# 组织架构与数据权限规则

## 1. 为什么需要组织架构

运营系统中常见场景：

```text
普通运营只看自己的产品
小组长看自己和组员的产品
主管看整个部门的产品
老板看全部
临时账号看指定 SKU / 店铺
```

这不能只靠角色完成，必须加入组织架构、产品负责人归属和页面数据权限。

## 2. 三者分离

```text
角色 = 能做什么
组织架构 = 属于哪个组、管谁
数据权限 = 在某个页面能看哪些数据
产品负责人归属 = 哪些产品 / SKU 归谁负责
```

## 3. 数据权限模式

```text
all              全部数据
own              仅自己负责的数据
direct_reports   自己 + 直属下级的数据
team             当前小组数据
org_tree         当前组织及所有下级组织数据
selected         指定店铺 / 指定负责人 / 指定 SKU
custom           自定义组合
none             无数据
```

## 4. 页面可单独配置

同一个用户在不同页面可以有不同数据范围：

| 页面 | 数据权限口径 |
|---|---|
| 产品管理 | 主运营 / SKU |
| 每日销售 | 主运营 / 店铺 / SKU |
| 广告总览 | 广告负责人 / 店铺 / SKU |
| 采购计划 | 采购负责人 / 供应商 / SKU |
| 库存预警 | PMC 负责人 / SKU / 仓库 |
| 利润中心 | 财务授权 / 店铺 / SKU |
| API文档 | 系统权限，不走产品范围 |
| 用户管理 | 系统权限，不走产品范围 |

## 5. 产品负责人类型

`core_product_owner.owner_type` 建议支持：

```text
main_owner        主运营
ads_owner         广告负责人
purchase_owner    采购负责人
pmc_owner         库存负责人
assistant_owner   协助负责人
```

必须支持：

```text
start_date
end_date
is_active
```

用于处理产品转负责人和历史归属。

## 6. 负责人历史口径

默认：

```text
权限过滤：当前有效负责人
绩效 / 奖金 / 历史复盘：历史负责人
运营看板：可支持当前负责人 / 历史负责人切换
```

## 7. 后端过滤原则

数据权限必须由后端强制执行。禁止让前端通过参数决定是否看自己的数据。

错误：

```text
?only_my_products=true
```

正确：

```text
后端根据当前用户、当前页面、当前数据权限自动添加 WHERE 条件。
```

## 8. 页面展示

`PageShell` 顶部应显示当前数据范围，例如：

```text
数据范围：仅自己负责的产品
数据范围：自己 + 直属组员
数据范围：全部数据
```


## 9. PR #287 — 账号限定店铺权限的业务合同（代码提交，待验证）

**授权粒度**：必须精确匹配 `source_account_ref|store_id`，例如同一个
`store_id` 出现在不同 `source_account_ref` 时属于两个不同身份。
业务接口始终先收紧账号范围，再将店铺范围按二元组合键与组织负责人范围取**交集**，
不允许前端筛选参数放宽授权范围。

- `source_account` 由已登记同步账号与有效用户角色范围决定；
- `org_department` 由最新飞书快照、有效员工和明确人工审核的负责人绑定决定；
- `store` 的角色/用户持久化范围仍遵循“用户同类型覆盖角色”的原有模型；
- 未指定 `store` 时不增加店铺限制；包含歧义的历史裸 `store_id` **拒绝**而
  不是按全局店铺授权；
- 当前实现仅覆盖经过独立审查的每日销售、Walmart Listing 和 PMC 采购看板
  明细路径，包括这些路径的列表、统计、筛选与导出（有导出接口时）；
- 对尚未证明店铺归属安全的财务、广告、库存、通用商品变更与其他路由，
  不开启新店铺范围的授予；`RbacService` 仍对新 `store` 授权返回 422，
  直至所有受影响业务模块完成隔离与复核。

### PMC 采购的交叉归属保护

采购单号、库存与采购 SKU 不自动代表单一负责人或单一店铺。
采购板受限列表可展示经 SQL 证明归属的明细及其行级分配金额，
但整单金额、采购总量、整单收货结果、跨负责人历史交期与样本不可借明细授权获取。
相关受限响应的 `scope_limited=true` 明确区分“无归属证据”与真实数值零；
被隐藏的整单/历史数值序列化为 `null`，不填充模拟值。
未确认归属的 SKU 周期列表、人工修正以及交期卡片明细筛选仍拒绝访问。

上述实现未运行完整 CI、真实 PostgreSQL 或业务人工验收，
**不能据此认定全平台 `store` 数据范围已经完成并可配置**。


## 10. PR #287 — 账号限定负责人、历史授权边界与拒绝诊断（代码已提交，待验收）

### 负责人复合身份

- `iam_org_owner_account_bindings` 使用 `(source_account_ref, owner_ref)`
  作为复合唯一键，与仅保存 `owner_ref` 的历史表隔离。
- 绑定仅可由超级管理员通过真实业务数据中的来源账号/负责人组合建立，
  且员工必须在最新飞书快照中处于可用状态。手工绑定、解绑均在
  `iam_org_owner_account_binding_events` 保留操作者与时间。
- 已审查的新数据过滤路径按**账号和 UID 两列同时匹配**：
  每日销售、Walmart Listing、PMC 采购、退款分析、WFS 异常及其审批、
  商品管理列表与详情。分页、汇总与导出使用相同的服务端边界。
- 有新复合绑定时，旧的无账号负责人 UID 不再拓展该账号的可见范围；
  尚未建立复合绑定的历史账号仍沿用已有的单账号歧义拒绝规则。
- 不允许通过员工姓名、店铺名称或同名 SKU 自动建立跨账号身份关联。

### 历史保存的数据范围

未完成全业务服务端过滤的 `owner`、`sku`、`product` 范围，即使过去
已保存到数据库，也不能被业务接口静默忽略。对持有这类范围的普通用户，
未完成的业务读取与写入一律拒绝；不会借助前端筛选条件推断有权限。

`org_department` 与明确审核过的员工自有负责人绑定同样对未审查的业务
路由实施拒绝。对于店铺范围，退款、WFS 异常及其关联审批也已按
`(source_account_ref, store_id)` 联合过滤。没有明细归属证据的财务、
跨负责人 SKU 周期、运营计划与其他旧业务接口不予放行。

> 此处的“拒绝”表示安全隔离，并非该维度的正常业务功能已经实现。
> 新建配置仍遵从角色/用户范围接口中的 422 限制，直到所有需覆盖的
> 服务端读写路径完成并经过验收。

### 403 拒绝诊断

- 拒绝响应继续包含 `X-Request-ID`，可供管理员查找对应事件。
- `iam_access_denial_events` 只持久化请求 ID、主体 ID、HTTP 方法、
  后端路由模板、权限键、错误类别和有限枚举的范围原因；**不存**
  URL 查询参数、请求体、Headers、Token、客户 ID、手机号或订单内容。
- `GET /api/settings/rbac/access-denials` 仅超级管理员可用，
  最多查询 100 条，支持按请求 ID 精确匹配。角色管理提供搜索入口。
- 记录保留 30 天；计划任务每日删除超过保留期的记录。
  诊断存储暂不可用时，原访问拒绝仍保持 403。

### 交付与授权边界

新迁移 `20261104_0074_account_owner_bindings` 和
`20261104_0075_access_denial_audit` 仅已提交到 PR #287。
没有执行生产数据库迁移、真实飞书对接、CI、部署或合并。
本文不得替代真实权限矩阵、跨账号数据验收或逐项任务签收。


## 11. PR #287 — 历史负责人／SKU／商品权限安全读取（代码已提交，待验证）

旧授权值只有在能精确解析为“`source_account_ref|业务身份`”时才可使用，
否则直接拒绝访问（HTTP 403），绝不将未限定账号的 UID/SKU/Item ID
解释为全部账号可见。用户级相同范围类型继续覆盖角色级范围，不以
页面搜索条件代替持久化授权。

- `owner`：业务身份为来源账号下的负责人 UID。仅在每日销售、
  订单利润和 Walmart Listing 的已审查 **GET** 路由执行；与飞书
  审核映射和店铺范围相交。不会在 PMC、售后、仓库、审批等模块静默忽略。
- `sku`：业务身份为来源账号下的**本地 SKU**，不自动映射为 MSKU
  或平台商品 ID。允许每日销售、订单利润与 Walmart Listing 的审查
  读取；订单利润必须证明整条日／账号／SKU 汇总完全由授权明细构成。
- `product`：业务身份为来源账号下的**平台 Item ID**，只允许每日
  销售及 Walmart Listing 已审查的 GET 查询、统计、筛选和导出；
  不允许读取可能包含其他 Item ID 的订单利润 SKU 汇总。
- 三种范围的写入路由、未审查页面、定价、跨业务聚合和通用数据导出
  均维持拒绝。商品管理的内部商品 ID 与 Walmart Item ID 不得
  混为一谈。
- `owner`、`sku`、`product` 的**新增授权配置仍保持禁用**
  （服务端返回 422），以防业务模块覆盖不完整造成越权承诺；
  本节只涉及历史已有授权的严格限制及特定读取链路。
- 403 拒绝诊断新增 `OWNER_SCOPE_NOT_ENFORCED`、
  `SKU_SCOPE_NOT_ENFORCED`、`PRODUCT_SCOPE_NOT_ENFORCED`
  三种受限原因，仅保存枚举标识，不记录真实授权值或商品标识。

该实现已加入 SQL 边界与未授权接口的契约测试，但未执行测试，
尚未在真实 PostgreSQL 上验证，更未运行生产数据回放。
