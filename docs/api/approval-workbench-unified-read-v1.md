# Unified approval workbench read API V1 (local candidate)

`GET /api/approvals/workbench/read` uses `ApprovalQuery` (`tab`, `view`, `approval_type`, `risk_level`, `keyword`, `page`, `page_size`, existing max 200). Page permission: `page:data-center:approval-workspace:view`; existing source account scope and per-business visibility; product cost uses `products:read`, existing product scope and purchase-cost field permission. No provider calls.

Envelope: `success`, `data`, `error`, `meta`, `request_id`.
`data.items`: existing ApprovalItem, optional clearance details, optional `purchase_read` for current-page new-product purchases. `data.business_counts`: real visible counts keyed by workbench category; frontend appends existing local demo rows/counts. `meta` is current page/page_size/real total. `purchase_read`: `application_id`, `version`, `source_account_ref`, `store_id`, `item_id`, existing Listing DTO or null, existing `evaluation_operating_daily` or null, `unit_purchase_cost_cny` numeric string or null. Approval evidence and application-month FX are in existing `purchase_details`. IDs are strings. No new metric definitions. A 409 indicates changed or inconsistent page/identity; refresh before action.

SOP: enter workbench or refresh; wait for the page result; click any new-product purchase row; the existing drawer consumes transferred data immediately, with no detail API in the verified cache path. Other business details retain existing endpoints. Approve/reject still use original authorized decision workflow; store options still queried when opening approve confirmation, not at detail open. On save reload the page; never reuse an old decision version. Compare screenshots, scores, profit, costs, totals and Network with pre-change behavior before approval. Candidate only; no production rollout.
