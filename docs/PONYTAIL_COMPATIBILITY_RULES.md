# Ponytail 项目兼容规则

## 文件用途

本文件用于把 Ponytail 的核心开发思想固化到项目仓库中。

即使某个开发者没有安装 Ponytail 插件，或者某个 AI 工具不支持 Ponytail，本项目内所有 AI 代码开发、修改、Review、重构建议和 PR 检查，也必须遵守本文件。

本文件不是官方 Ponytail 插件本体，不包含官方 hooks，也不会自动安装到 Codex / Claude Code。它是项目级默认开启规则，用来保证所有 AI 都按同一套“少做过度设计、优先复用、最小正确实现”的原则工作。

没有官方 hooks，就不是完整官方 Ponytail。因此，支持官方 Ponytail 插件的工具应优先安装官方插件；本文件用于在插件未安装、安装失败或工具不支持插件时提供项目级兜底。

## 默认开启规则

Ponytail 在本项目中**默认开启**。

它不是需要用户手动调用的业务 Skill，也不是只有用户写出“使用 Ponytail”时才生效的可选能力。

只要任务涉及代码开发、代码修改、重构、Bug 修复、Code Review、PR 自检、技术方案收敛或依赖选择，AI 就必须自动执行本文件。

AI 不得：

1. 要求用户特意引用 Ponytail。
2. 把 Ponytail 当成“本次是否需要选择的 Skill”。
3. 因为用户没有提 Ponytail 就跳过本文件。
4. 因为当前 AI 工具未安装官方 Ponytail 插件就跳过本文件。
5. 在开发计划中把 Ponytail 标记为“本次不需要”。

正确做法：

```text
项目规则读取完成
↓
Ponytail 默认开启
↓
Skill 自发现
↓
最小正确实现检查
↓
开发计划
↓
用户确认
↓
修改代码
```

本项目中的 Ponytail 是**默认开发原则**，不是可选技能。

## 官方插件优先安装规则

本项目要求 AI 主动帮助开发者安装官方 Ponytail 插件，而不是等待开发者自己阅读说明。

首次接手项目时，AI 必须读取：

```text
AI_ONBOARDING.md
docs/tools/AI_TOOLS_FIRST_RUN_SETUP.md
docs/tools/PONYTAIL_INSTALL_GUIDE.md
```

如果当前工具支持官方 Ponytail 插件，并且当前 AI 有终端执行能力，AI 应在用户确认后执行：

```bash
bash scripts/setup-ai-tools.sh
```

官方 Ponytail 插件优先级：

```text
官方 Ponytail 插件 + hooks
↓
项目内置 Ponytail 默认规则
```

如果官方插件未安装、无法安装或当前工具不支持插件，AI 不得跳过 Ponytail 原则，必须继续执行本文件。

AI 不得自动替用户信任 hooks。hooks 必须由用户审查并确认。

---

## 最高优先级

项目规则永远高于 Ponytail 简化原则。

优先级顺序：

```text
AGENTS.md
AI_DAILY_RULES.md
old-system 只读规则
固定技术栈规则
单功能 / 单页面开发规则
API / 数据库 / Celery / 权限 / 财务 / 测试规则
本文件的 Ponytail 兼容规则
```

AI 不允许因为追求“少写代码”而省略项目强制要求。

以下内容不得被 Ponytail 简化原则削弱：

1. `old-system/` 只读规则。
2. 禁止复制旧系统代码。
3. 安全和密钥保护。
4. 权限校验。
5. 操作日志。
6. API 契约。
7. Pydantic 数据校验。
8. SQLAlchemy / Alembic 迁移规则。
9. Celery 幂等性、重试、失败处理。
10. 外部 API 限流、超时、错误处理。
11. 数据来源和字段血缘。
12. 财务公式、币种、时间口径。
13. Loading / Empty / Error / Pagination。
14. 测试、验收、回滚方案。
15. 维护型注释。

## Ponytail 开发梯子

AI 写代码前，必须按顺序问自己：

```text
1. 这个功能真的需要新增代码吗？
   不需要：不要写。

2. 项目里已经有类似组件、Hook、Service、Repository、工具函数吗？
   有：优先复用，不要重写。

3. 标准库或语言内置能力能解决吗？
   能：优先使用标准库。

4. 浏览器、HTML、CSS、Ant Design、ProComponents、FastAPI、SQLAlchemy、Pydantic 是否已有原生能力？
   有：优先使用已有平台能力。

5. 项目已安装依赖能解决吗？
   能：使用现有依赖，不新增依赖。

6. 一两行简单代码能清楚完成吗？
   能：不要抽象出复杂模块。

7. 只有前面都不成立时，才实现最小正确方案。
```

这叫“最小正确实现”，不是“最少代码”。

## 允许的简化

AI 可以并且应该：

1. 删除没有需求依据的未来扩展。
2. 避免为了“以后可能用到”提前设计抽象层。
3. 避免重复写相同 UI、请求、类型、SQL、校验逻辑。
4. 优先复用项目已有组件和后端模块。
5. 优先使用 Ant Design / ProComponents 已有能力。
6. 优先使用 FastAPI / Pydantic / SQLAlchemy / Celery 的正常能力。
7. 用简单清晰的代码替代炫技代码。
8. 控制单次任务范围，只完成本次闭环。
9. 在不损害安全和可维护性的前提下，减少文件数量和代码量。
10. 对过度设计主动提出更小方案。

---

## 禁止的“伪简化”

AI 不允许：

1. 用“简单”为理由跳过权限校验。
2. 用“快速”为理由跳过数据校验。
3. 用“少写代码”为理由不处理错误状态。
4. 用“最小实现”为理由不写必要测试。
5. 用“减少文件”为理由把页面写成巨型文件。
6. 用“减少分层”为理由把业务逻辑堆进 Route。
7. 用“少改动”为理由复制粘贴旧逻辑。
8. 用“省 token”为理由忽略 `old-system/` 只读边界。
9. 用“先跑起来”为理由跳过 Alembic migration。
10. 用“后面再补”为理由省略财务口径、字段来源和操作日志。

---

## 新依赖控制

AI 不得主动新增依赖，除非同时满足：

1. 项目现有依赖无法合理完成。
2. 标准库或平台原生能力无法完成。
3. 新依赖是本任务必要条件，不是为了省几行代码。
4. 已说明替代方案和拒绝原因。
5. 已说明依赖体积、维护风险、安全风险。
6. 用户明确确认。

尤其禁止为以下简单场景新增依赖：

- 日期输入。
- 颜色选择。
- 简单表格展示。
- 简单弹窗。
- 简单导出。
- 简单状态管理。
- 简单字符串处理。
- 简单金额格式化。

## React 前端适用规则

前端使用 Ponytail 时，必须与组件封装规则一起执行。

AI 应优先复用：

1. 已有页面布局。
2. 已有表格组件。
3. 已有筛选表单组件。
4. 已有 API Client。
5. 已有 Hook。
6. 已有 Type。
7. 已有工具函数。
8. Ant Design / ProComponents 原生能力。

AI 不允许：

1. 为一个页面复制一套独立请求层。
2. 为简单表格重新造轮子。
3. 为简单表单引入第二套表单库。
4. 为局部状态引入新的全局状态方案。
5. 把所有逻辑写在一个 Page 文件里。
6. 不处理 Loading / Empty / Error / Pagination。

---

## FastAPI 后端适用规则

后端使用 Ponytail 时，必须与分层规则一起执行。

AI 应优先复用：

1. 已有 Router 结构。
2. 已有 Schema 约定。
3. 已有 Service 模式。
4. 已有 Repository 模式。
5. 已有 Model。
6. 已有权限函数。
7. 已有操作日志函数。
8. 已有外部 API Integration。
9. 已有 Celery 任务模板。

AI 不允许：

1. 为了少文件，把业务逻辑全部写进 Route。
2. 为了少代码，绕过 Service / Repository。
3. 为了快速，直接拼接 SQL。
4. 为了省事，跳过 Pydantic Schema。
5. 为了简单，把 Celery Task 写成业务大杂烩。
6. 为了少改动，复用 `old-system/` 代码。

## 开发前必须输出 Ponytail 检查

每次写代码前，AI 必须在开发计划中增加：

```md
## Ponytail 最小正确实现检查

1. 本次功能是否真的需要新增代码：
2. 是否已有可复用组件 / Hook / Service / Repository：
3. 是否可用标准库、平台原生能力或现有依赖：
4. 是否需要新增依赖：
5. 是否存在过度抽象风险：
6. 是否存在重复代码风险：
7. 本次最小正确实现边界：
8. 哪些未来扩展本次不做：
9. 哪些项目强制规则不能被简化：
```

用户确认前，不得修改代码。

---

## 完工后必须输出 Ponytail 检查

完成后，AI 必须说明：

1. 本次是否只实现了需求范围内的代码。
2. 是否复用了已有组件或模块。
3. 是否新增依赖；如新增，说明用户确认记录。
4. 是否存在重复代码。
5. 是否存在过度抽象。
6. 是否保留必要校验、权限、日志、错误处理和测试。
7. 是否违反 `old-system/` 只读规则。

---

## 官方 Ponytail 插件的使用关系

官方 Ponytail 插件是增强项，不是本项目规则生效的前提。

如果当前 AI 工具已经安装 Ponytail 插件，可以使用 Ponytail mode。

如果当前 AI 工具没有安装 Ponytail 插件，也必须按本文件执行。

用户不需要在任务中再次提醒“使用 Ponytail”。AI 只要进入本项目代码任务，就必须默认开启本文件。

官方插件只能作为辅助，不得覆盖项目规则。

禁止把官方插件安装写入 `npm install`、`postinstall`、CI、Vercel 构建或 Docker 构建流程。

安装 Codex / Claude Code 插件属于每个开发者自己的 AI 工具配置，不属于项目运行依赖。
