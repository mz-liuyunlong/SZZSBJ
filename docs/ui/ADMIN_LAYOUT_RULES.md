# Admin Layout Rules

本文件只定义后台页面的固定布局要求和 UI 组件使用要求。
Codex 不得因为布局规则引入新的技术栈、替换既定前端框架、替换既定 UI 组件库，或复制外部后台模板代码。

## 1. 页面整体布局规则

1. 前端必须采用统一的企业级后台管理系统布局。
2. 所有业务页面必须在统一 `MainLayout` 内展示。
3. `MainLayout` 必须固定包含以下区域：左侧 `Sidebar` 主导航、顶部 `Header` 顶部栏、顶部 `Tabbar` 页面标签栏、`Breadcrumb` 面包屑导航、页面内容区。
4. 禁止每个页面单独实现自己的整体布局。
5. 禁止业务页面绕过 `MainLayout` 直接渲染内容。
6. 禁止不同模块使用不同布局风格。
7. 页面布局必须保持统一、紧凑、清晰，适合长期运营后台使用。
8. 所有页面的布局状态、菜单状态、标签页状态、面包屑状态，必须由统一配置或统一布局组件管理。
9. 新增页面时，必须先接入统一布局，再开发页面内容。
10. 没有接入统一布局的页面，不得标记为 `ready`。

## 2. 左侧导航规则

1. 系统必须使用左侧 `Sidebar` 作为主导航。
2. `Sidebar` 必须支持一级菜单、二级菜单，后续可扩展多级菜单。
3. `Sidebar` 必须支持折叠与展开。
4. `Sidebar` 折叠后必须保留菜单图标展示。
5. 当前路由对应的菜单项必须高亮。
6. 菜单必须从 `frontend/src/config/navigation.ts` 自动生成。
7. 禁止在页面组件中手写菜单。
8. 禁止在 `routes.tsx` 中重复维护菜单结构。
9. 菜单项必须支持基础字段：`key`、`title`、`path`、`icon`、`permissionKey`、`status`、`badge`。
10. 没有权限的菜单项不得展示。
11. 被禁用、隐藏或未开放的菜单项，必须通过 `navigation.ts` 的状态字段控制。
12. `Sidebar` 的宽度、折叠宽度、间距、图标大小、选中态、悬浮态必须统一。
13. 新增一级或二级菜单，必须先更新 `navigation.ts`，不得直接在布局组件里新增。
14. `Sidebar` 不负责业务逻辑，只负责导航展示、权限过滤和当前路由高亮。

## 3. 顶部栏规则

1. 所有页面必须使用统一 `Header`。
2. `Header` 必须由 `MainLayout` 统一渲染。
3. 禁止业务页面单独实现 `Header`。
4. `Header` 必须预留入口：`Sidebar` 折叠按钮、全局搜索入口、刷新当前页面、通知入口、帮助入口、用户菜单、主题切换预留。
5. `Header` 中的用户菜单必须预留当前用户信息、个人设置入口、退出登录入口。
6. `Header` 中的通知入口必须预留后续接入系统通知、任务通知、预警通知。
7. `Header` 中的帮助入口可以跳转到当前页面帮助文档或帮助中心。
8. `Header` 高度、背景、阴影、边框、间距必须统一。
9. `Header` 不允许承载具体业务页面逻辑。
10. 不同页面不得自行修改 `Header` 布局结构。

## 4. Tabbar 规则

1. 系统必须启用顶部页面标签栏 `Tabbar`。
2. 用户打开页面后，该页面必须在 `Tabbar` 中显示为一个标签。
3. `Tabbar` 标题必须来自 `navigation.ts` 或 `route meta`。
4. 禁止页面组件自行创建 `Tabbar`。
5. `Tabbar` 必须由 `MainLayout` 统一渲染。
6. `Tabbar` 必须支持基础操作：关闭当前标签、关闭其他标签、关闭全部标签、刷新当前标签页。
7. `Tabbar` 必须预留固定常用页面功能。
8. 当前激活页面对应的标签必须高亮。
9. `ComingSoon` 页面也必须进入 `Tabbar`。
10. 没有权限访问的页面不得出现在 `Tabbar`。
11. 被关闭的标签不得影响用户登录状态和全局权限状态。
12. `Tabbar` 不允许保存敏感参数、Token、Secret 或完整请求内容。
13. `Tabbar` 的展示顺序、标题、图标、关闭状态必须由统一状态管理。
14. 业务页面不得直接操作 `Tabbar` 数据，必须通过统一方法打开、关闭或刷新标签。

## 5. 面包屑规则

1. 所有正式页面必须显示 `Breadcrumb` 面包屑导航。
2. `Breadcrumb` 必须由 `navigation.ts` 或 `route meta` 自动生成。
3. 页面组件不得手写面包屑文本。
4. `Breadcrumb` 层级必须对应：一级导航 > 二级导航 > 页面内部 Tab / 详情页。
5. `Breadcrumb` 必须由 `MainLayout` 或统一布局组件渲染。
6. 页面标题不能替代 `Breadcrumb`。
7. `ComingSoon` 页面也必须显示正确 `Breadcrumb`。
8. 隐藏页、详情页、编辑页如果没有左侧菜单入口，也必须通过 `route meta` 配置 `Breadcrumb`。
9. `Breadcrumb` 文案必须和 `navigation.ts` 中的菜单标题保持一致。
10. `Breadcrumb` 点击上级节点时，应返回对应上级页面或模块入口。
11. 没有明确上级页面的详情页，必须至少显示所属模块和当前页面标题。
12. 没有 `Breadcrumb` 的页面不得标记为 `ready`。
13. 禁止不同页面使用不同的面包屑样式。
14. `Breadcrumb` 不负责权限判断，权限过滤必须在路由和菜单层完成。

## 6. UI 组件使用规则

1. 前端页面必须使用项目既定 UI 组件体系：`Ant Design + ProComponents`。
2. 基础布局、菜单、按钮、弹窗、标签、状态提示等，必须优先使用 `Ant Design`。
3. 后台表格页面必须优先使用 `ProTable`。
4. 后台表单页面必须优先使用 `ProForm`。
5. 数据卡片、统计卡片、后台业务卡片优先使用 `Card`、`Statistic`、`ProCard`。
6. 禁止业务页面用原生 HTML + 自写 CSS 手写复杂后台组件。
7. 禁止每个页面单独发明表格、表单、弹窗、标签、卡片、状态提示、分页、筛选器样式。
8. 禁止引入第二套 UI 组件库。
9. 禁止为了单个页面临时安装新的 UI 框架、图标库、表格库、表单库。
10. 只有在既定 UI 组件无法满足业务场景时，才允许封装自定义组件。
11. 自定义组件必须基于既定 UI 组件库二次封装，不得完全脱离 UI 组件体系。
12. 如果页面大量使用原生 `div`、`table`、`form`、`button` 实现后台组件，该页面不得标记为 `ready`。
