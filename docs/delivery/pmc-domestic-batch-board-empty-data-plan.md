## 1. 结论

本次优先核实线上环境配置、来源范围和发布数据，暂不修改列表查询代码。

接口返回 `200`、`meta.data_status=not_published`、`meta.publication_ids=[]`、`data.total=0`，表示当前账号和仓库范围没有匹配的当前成功发布版本。它不能证明数据库完全没有来源数据，也不能直接证明从未发布过。

保留“看板读取已发布 MART”的设计。若已有完整 ODS，但缺少看板版本，应复用现有构建与发布程序；若需要以后采集完成自动更新看板，再单独开发任务编排。

## 3. 页面与接口的数据链路

页面路由与 API 路径不同，页面实际请求：

| 用途 | 方法与路径 |
|---|---|
| 表格列表 | `GET /api/pmc/domestic/inbound-batches` |
| 统计 | `GET /api/pmc/domestic/inbound-batches/summary` |
| 店铺、负责人等选项 | `GET /api/pmc/domestic/inbound-batches/filter-options` |

当前本地代码的查询链路：

```text
来源账号范围 + 仓库范围
    → gov_domestic_board_publications
      source_account_ref 匹配
      source_warehouse_id 匹配（指定仓库时）
      is_current = true
      status = published
    → mart_domestic_inbound_batch_board
    → 业务筛选、分页、统计
    → 前端展示
```

`InboundReadService._meta()` 根据是否存在可见发布版本设置 `data_status`。区别如下：

| 返回状态 | 含义 |
|---|---|
| `not_published`，版本数组为空 | 当前账号、仓库范围没有当前成功发布版本 |
| `ready`，存在版本，列表为空 | 已有发布；当前筛选无记录，或该版本确实是空发布 |
| 接口报错 | 请求、权限、服务或数据库异常，不能当作正常空数据 |

普通店铺、SKU、日期筛选通常不会令发布版本数组变空。当前排查重点应放在环境、账号、仓库及发布版本，而不是先调整普通列表筛选。

超级管理员的 `*` 权限不会生成发布数据。来源账号范围仍由对应依赖确定，不能仅凭超级管理员身份认定所有账号数据都可见。

店铺和负责人选项依赖当前可见 MART 行，再关联店铺维度和负责人来源；没有发布行时，选项为空符合代码行为。日期能否展示还取决于来源日期和时区证据；有发布并不保证所有日期字段都有值。

| 当前版本展示行 | 1441 行 |
| 发布表累计记录 | 2 条 |

| 流水覆盖窗口 | 2026-09-21 至 2026-10-21，结束不含 |

这些是历史执行文档记录，不是本次线上数据库检查结果。当前接口无发布版本与该记录存在差异，需要优先确认：

1. 当前线上后端是否连接了历史发布所在数据库和 schema。
2. 历史版本是否属于 `primary` 和当前仓库范围。
3. 是否发生过环境重建、数据恢复、迁移遗漏或当前版本标记变化。
4. 当前部署代码是否与本地分析版本一致。

不能直接用历史的 1441 行作为当前线上应有数量，也不能把 10 月 20 日快照当作今天库存。

## 5. 第一阶段 只读核实

由具备目标环境读取授权的人员执行。读取结果仅保留环境指纹、账号、仓库、版本、状态、数量和时间等必要信息，不输出连接串、Token 或 RAW 全量内容。

| 顺序 | 检查内容 | 需要得到的证据 |
|---|---|---|
| 1 | 线上 API 实际环境、数据库与 schema | 与历史发布环境是否一致；不回显凭据 |
| 2 | 实际请求仓库参数及服务端来源范围 | 是否确为 `primary`，是否限制到目标仓库 |
| 3 | 发布表全部相关版本 | 账号、仓库、状态、当前标记、来源 run、发布时间 |
| 4 | 发布版本对应 MART | 行数、账号/仓库一致性、版本关联是否完整 |
| 5 | W1/W3 同步 run | 是否成功、接口类型、来源账号、时间窗口 |
| 6 | ODS 与 RAW 引用 | 所选 run 是否仍有完整且可重放的来源证据 |

第一阶段输出应明确落入下一节的一种处理分支，不执行发布、切换版本或修改配置。

## 6. 第二阶段 按原因处理

| 核实结果 | 处理方案 | 类型 |
|---|---|---|
| API 连错数据库或 schema | 核对目标环境后，单独审批连接配置修正及生效方式 | 配置变更 |
| 账号或仓库归属与请求不一致 | 确认真实业务归属，再调整授权配置、请求范围或单独评估映射问题；不直接批量改账号值 | 配置或映射修复 |
| 已有完整正确版本，仅当前标记异常 | 验证版本及关联数据后，受控恢复当前版本；同时追查标记异常原因 | 数据修复 |
| 无可用发布版本，W1/W3 ODS 完整 | 使用现有构建器先隔离重放和对账，通过后受控发布 | 数据发布 |
| ODS 缺失、run 失败、窗口不连续或证据不足 | 仅补齐明确缺失的来源范围，再构建发布 | 采集与数据发布 |
| 已有代码无法通过合法来源数据，或与部署版本不一致 | 保留失败证据，定位具体缺陷，另立修复任务 | 代码修复或版本核实 |

现有发布入口：`backend/scripts/publish_pmc_domestic_inbound.py`。它需要显式指定账号、仓库、W1 成功 run、一个或多个 W3 成功 run及已确认的来源时区，并有独立发布授权门禁。

现有 `InboundPublisher.publish()` 已实现：

- 校验所选 run 成功、来源账号一致、接口类型正确。
- 检查 W1 包含零库存证据、W3 窗口有效且连续、来源引用存在。
- 使用 ODS 构建入库单 × SKU × 店铺投影，补充现有报关证据。
- 按账号和仓库获取事务锁，追加新发布版本及 MART 行。
- 同一事务切换当前版本；异常回滚，保留之前已提交的版本。

因此，“有 ODS、缺发布”通常不需要重写列表接口或新建表。现有校验不等于已覆盖所有业务对账，正式发布前仍需核对数量、重复身份、覆盖范围和关键字段。

历史 run 可以用于恢复历史展示，但若需要当前库存，应另行确定新的采集时间与覆盖范围。

## 7. 第三阶段 采集与发布自动衔接

此阶段属于后续代码开发，需要先完成数据源决策和 PRP 确认。本次不实施。

复用现有 Redis、Celery、同步审计和任务中心，增加以下编排：

```text
确认账号、仓库、覆盖范围
    → W1 完整快照成功 + 所需 W3 窗口全部成功
    → 固定本次来源 run 集合
    → 构建候选结果与质量检查
    → 对账通过
    → 原子发布
    → 记录版本、来源时间、覆盖范围和任务结果
```

开发范围建议：

1. 明确 W1/W3 配对与快照时间兼容规则，避免任意拼接不同批次来源。
2. 增加发布幂等控制，以账号、仓库、规范化来源 run 集合和构建规则版本等确定发布身份；来源时区等影响结果的参数也必须参与判定。
3. 同范围并发发布受控，失败保留旧成功版本，重试不重复生成相同发布。
4. 在现有任务中心展示采集与发布各自状态、失败阶段、安全错误码和重试入口。
5. 在看板区分尚未发布、成功空发布、旧版本仍可用及刷新失败；显示真实数据时间和覆盖范围。

列表 GET 继续只读，不在打开页面时触发采集或发布，不降级读取 ODS，也不以示例数据替代真实数据。

## 8. 验收与回滚

### 恢复验收

- API 环境与目标数据库、schema 已核实。
- 目标账号和仓库存在唯一当前成功版本，关联 MART 完整。
- 列表返回 `ready` 和非空版本数组；记录数与对账结果一致，不能预设必须为 1441。
- 列表、统计在同一发布版本下核对；店铺、负责人仅展示可见且有证据的选项。
- 入库父数量按入库单 × SKU 去重，跨店铺不能重复求和；未知数量不补零。
- 日期、库存快照时间、覆盖范围与来源证据一致。
- 权限范围不扩大，旧 ODS、RAW 和历史发布不删除，不修改已有打包单引用。

### 后续开发验收

在隔离测试环境覆盖成功发布、成功空发布、缺失来源、窗口断档、重复触发、并发发布、失败回滚和账号隔离。前端按项目要求完成对应 E2E，不依赖生产库或真实平台凭据。

### 回滚

配置修正应记录变更前后目标及恢复步骤。版本切换应保留旧版本；回退前核实该版本与已有业务引用的兼容性。首次发布没有旧版本时，失败依赖事务回滚；发布成功后的撤回另行评估，不删除来源证据或直接清空 MART。
