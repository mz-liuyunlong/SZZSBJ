## 用户可直接理解的目标

每条异常不展示孤立的英文错误码，而说明：这是什么问题、现有证据、差多少、需要我提供什么、系统可自动处理什么、下一步按钮、处理结果。

首批基于生产只读证据的异常（primary）：SEM Campaign 90、SEM 40、SP 16、送样超 SaleStat 5，共151条；截至2026-11-20，audit 0条。不要把5条送样异常误认为5笔送样，已确认4个不同订单明细及1条日期级汇总。

## 第二阶段：待规则确认后的真实操作能力

### 自动复核（只读取内部事实）

- 新增面向当前异常 ID 的 diagnosis 读取接口（integrations:read）。
- 分配给后端服务，按 source_account_ref + business_date + subject_key 边界核对、返回差异，不能直接批量读取外部 API。
- 按异常类型分支：送样比较样本事实与 SaleStat、订单当前身份及日期；广告检查 SEM/SP 对应 Campaign/Item ID 归属。
- 通过核对 ≠ 自动改账；必须判定是否需要物理修正、是否已计入利润、当前业务日是否锁定。

### 补数 / 人工确认

- 用户填最小业务字段，如订单号、有效 Item ID、商品对应关系、SaleStat 业务日、Campaign 对应商品或明确分摊依据。
- 字段按异常类型显示，支持来源文件或凭据引用（必须使用既有文件能力或独立批准上传接口，不能承诺附件上传已存在）。
- 写入专用、带版本和审核痕迹的人工修正层 L10；原始 API/RAW、FACT 不直接改动。
- 对每一项变更保存 actor、变更前后、证据、业务日及重算批次；审核与冲突控制需明确。
- 「单纯人工确认」仅用于查明是合法的统计口径差异、无需财务修正的异常；记录确认依据，不允许借此扣除超额金额。

### 重算并复验

- 只对已确认业务日/店铺/Item ID 触发既有受控任务（Celery），有幂等键、并发锁、日期锁和版本预览。
- 预览差异：送样、销售额、广告费、利润及异常状态，用户确认后才写入。
- 重算成功且全部核验条件满足自动改 resolved；未通过保持 review_pending，附原因及重试入口。
- 对超出 SaleStat 的送样：送样身份保留，但不能将超额数量/金额强行扣减到负数；如 SaleStat 统计口径不包含零元样品，独立记录差异并根据批准的财务口径处理。
- 如果重算会修改已结算/锁账历史财务数据，默认禁止，单独审批。

## 未定决策（BLOCKED_BY_OWNER_DECISION）

1. 当 SaleStat 数量少于有效零元订单数量，且来源确认 SaleStat 口径不包含部分送样时，销售及利润究竟采用哪种权威基数？是否允许仅以人工确认关闭？需要明确避免漏算收入、成本或双扣。
2. 人工修正是否需要两人审核，哪类字段仅管理员可录入？沿用 integrations:update/execute 或引入经批准权限？
3. 人工凭据保存方式（文件上传还是来源链接），保持审计和权限控制。
4. 历史财务锁账日期和更正流程。
5. 送样、SEM、SP 三种异常的可复核通过条件各自独立定义，不以人工关闭替代财务验证。

在以上答案确认前，禁止编码财务补录、重算写入和自动关闭接口。
