# 代码上线 SOP（本地仓库 → 生产机）

> 目的：把"开发写的代码怎么落到生产机"这条流水线写死，避免每次靠口口相传、避免整目录同步冲掉线上独有改动。
> 适用：任何对 `/opt/lingxing-auto` 的代码/配置变更。基准以执行当天为准。
> 本文档为既有实践的固化，来源：`docs/销售驾驶舱_v1_部署与验收.md`、`v2_部署与验收.md`、`v1_阶段总结.md`。

## 0. 三个角色（先分清谁做什么）

- **代码 AI（开发侧）**：只写代码，落到 **Mac 本地仓库** `/Users/chen/Documents/New project`。不直接碰生产机。改现有文件时按真实内容改（旧块命中=1 才替换），改完本地自检。
- **部署 AI（运维侧）**：从 Mac 本地仓库把改动 **按白名单 `scp` 逐文件** 推到生产机 `company-ai:/opt/lingxing-auto`，再在生产机做 install / build / 建表 / 重启 / 验收。**部署 AI 人在生产机，看不到 Mac，除非文件已落到 Mac 仓库。**
- **需求方（Rocky）**：拍板范围、顺序、上线时机；在两侧之间传递。

## 1. 铁律（这条流水线特有的坑）

1. **生产机 `/opt/lingxing-auto` 不是 git work tree** → 不能 `git pull`。
2. **禁止整目录 `rsync`**。历史教训：md5 对比发现线上有 17 个本地没有的文件、且 `App.tsx`/`package.json` 本地与线上不一致；整目录同步会冲掉线上独有改动。
3. **只做白名单 `scp` 指定文件**：本次要动哪几个文件，就只推哪几个。
4. **覆盖现有文件前，先备份线上原文件**（如 `xxx.bak.YYYYMMDD_HHMMSS`），再 `scp` 覆盖。新增文件（线上原本没有）无需备份。
5. **部署前对账**：对每个"要覆盖的现有文件"先 md5 对比 local↔线上。若线上版本与本地不一致（线上有独有改动）→ **先把线上版回拉到本地对齐、合并改动，再推**，绝不用本地旧版直接盖掉线上新版。
6. 密钥只从 `.env` 读，不硬编码、不打印；**不动 cron 调度**（除非明确指令）。
7. **部署侧严禁修改代码**（2026-08-18 整改批A实测踩过：部署AI自行"修正TypeScript类型"重新落盘，md5 与交付不符且改动内容双方无底）。tsc 报错、类型不兼容、任何编译/运行问题 → **停手、贴出完整报错回报**，由代码侧修复后重新交付。目标 md5 与交付清单不符 = 部署未按交付执行，验收一律不予通过。

## 2. 标准流程（每次上线照做）

### 2.1 开发侧（代码 AI，在 Mac 本地仓库）
1. 改前核查真实代码/表结构，禁臆测。
2. 新功能隔离开发；改现有文件走"旧块→新块"最小改动。
3. 本地 `tsc --noEmit` 自检（依赖若有新增，需先在能联网环境 `npm install` 后再自检）。
4. 明确交付清单：**哪些是新增文件、哪些是覆盖现有文件**（覆盖的要标出来，供部署侧备份）。
5. **禁止在 if / else-if 链中间插入独立 `if` 语句**（2026-08-20 生产事故教训）：这会把该 `if` 之后的所有
   `else if` / `else` 分支「改嫁」给新插入的 `if`，链尾的兜底 `else` 会在每次条件不成立时被执行。
   实测后果：App.tsx 权限闸门插在渲染链中间 → **全站所有页面都渲染成兜底的 AI 助手页**；
   `tsc --noEmit` **完全查不出**（语法合法、类型正确，纯逻辑截断）。
   正确做法：①作为链中的 `else if` 分支；②或放在**整条链结束之后**做覆盖式赋值（推荐用于权限/兜底覆盖）。
   改动任何 if/else 链前，必须先通读**整条链到最后一个 else**，确认插入点不破坏结构。
6. **前端逻辑改动的验收不能只看 tsc/build**：必须实际打开 2~3 个**不同类型**的页面复验渲染
   （本次事故 tsc 0 错误、build 成功、冒烟 302/401 全绿，故障仍然发生，只有肉眼开页面才能发现）。

### 2.2 运维侧（部署 AI，Mac → 生产机）
1. **对账**：对每个"覆盖现有文件"做 md5 对比 local↔线上；不一致先回拉对齐（见铁律 5）。
2. **备份**线上被覆盖文件。
3. **白名单 `scp`** 逐文件推送到 `/opt/lingxing-auto/...` 对应路径。示例：
   ```bash
   # 备份线上被覆盖文件
   ssh company-ai "cp /opt/lingxing-auto/src/adminServer.ts /opt/lingxing-auto/src/adminServer.ts.bak.$(date +%Y%m%d_%H%M%S)"
   # 白名单 scp
   scp "src/adminServer.ts" company-ai:/opt/lingxing-auto/src/
   scp "package.json"        company-ai:/opt/lingxing-auto/
   ```
4. **依赖/类型自检**（依赖或 @types 有变时）：
   ```bash
   ssh company-ai "cd /opt/lingxing-auto && npm install && npx tsc --noEmit"   # 必须 0 报错
   ```
5. **前端构建**（改了 admin-frontend 时）：
   ```bash
   ssh company-ai "cd /opt/lingxing-auto/admin-frontend && npm run build 2>&1 | tail -8"
   ```
6. **建表/数据**（有 SQL 时）：`mysql walmart_ai_data < /opt/lingxing-auto/sql/xxx.sql`。建表用 `IF NOT EXISTS`，不覆盖既有表/不删历史/不清运营人工记录。
7. **重启服务**：
   ```bash
   ssh company-ai "sudo systemctl restart lingxing-admin.service && sleep 3 && sudo systemctl status lingxing-admin.service --no-pager | head -10"
   ```
7.5 **nginx 前缀放行（新增 API 一级前缀时必做，2026-08-18 批3a实测踩坑固化）**：生产 nginx（`/etc/nginx/sites-enabled/default`）对 `/api/*` 是**逐前缀 location 名单制**，新增一级前缀（如 `/api/profit-v2`）必须同步加 `location /api/<前缀>/ { proxy_pass http://127.0.0.1:3001; }` 并 `nginx -t && reload`。漏配的表现：3001 直连正常、经 80 端口 404 text/html（SPA兜底），页面报 "<html> 不是 JSON"。凡部署单含新 API 前缀，本步为必含字段。
    ⚠️ nginx 配置备份**严禁放在 `/etc/nginx/sites-enabled/` 或任何被 include 的目录内**——nginx 会把 `.bak.*` 当有效站点加载，直接 `nginx -t` 报 duplicate default server（2026-08-18 实测踩过，被迫回滚）。备份一律放 `/etc/nginx/backups/`（不存在先 mkdir）。
8. **只读验收**：curl 已知好接口确认服务活着；任一步失败即停下回报，**先别回滚、先只读诊断**（一个对照定位问题，参考端口那次经验）。
9. **context 镜像同步（强制收尾步，缺此步不算部署完成）**：把本次改动涉及的 `context/*.md` 从 Mac 单向覆盖到 `company-ai:/opt/lingxing-auto/context/`，并按 §3.8.1 五项验收（本地 hash → 上传 → 远端存在 → 远端 hash SAME → 行数/字节一致）。
   - **闸门 A · 漂移闸门（覆盖前必过）**：生产端目标文件的 md5 **只允许是两种值之一**——「上一次同步后记录的已知版本」或「本次要推的新版」。出现**第三种 md5** 说明有人在生产直接编辑过（`context` 单写入方制度禁止此行为），**立即停止、一个文件都不许覆盖**，先把生产版本回拉比对。
     判据是「确实是我预期的那个旧版」，**不是**「和新版不同」——后者等于无条件覆盖生产上的任何东西，会把他人改动直接抹掉。因此每次同步后必须记录当次 md5，作为下一次的闸门基线。
   - **闸门 B · 反向分叉检查（覆盖前必过）**：必须用 `comm -23`（生产独有）对**标题集合**做全量比对，输出为空才算通过；同时对共有标题做正文分叉比对（`diff_titles` 必须为 0）。
     **禁止只比条目数量**：数量是集合大小的投影，生产完全可能「既有 1 条独有、又缺 2 条」，净值反而更小而蒙混过关。2026-07-31 曾真实发生双写分叉，此闸门不可简化。
     操作：把生产 `TASK_CHANGE_LOG.md` 拉到本地临时文件后再比对；**临时文件操作必须串行**，并行会产生竞态导致 `No such file or directory`（2026-08-15 实测踩过）。

     **⚠️ 闸门B-1 的已知缺口（2026-08-21 实测踩到，必读）**：`comm -23` 比的是**标题全字符串**，
     因此**同一条目的状态后缀更新会被误报成「生产独有」**。实例：生产是
     `## … UI_STANDARDS 合规整改：… — 本地完成待部署`，本地已改为 `… — 已上线✅`，
     两者被当成两条不同标题，`生产独有条数 = 1`，闸门拦下。
     **处置纪律（不许简化）**：
     a. **不许因为"看起来只是状态更新"就放行**。闸门拦下就是拦下，必须拿证据推翻，不能拿判断推翻。
     b. **先对行数账**：`生产行数 + 本地新增条目行数` 是否等于 `本地行数`。对不上，说明中段还有差异，
        绝不能只按"标题后缀变了"解释（2026-08-21 实测差 6 行，是上线后补的部署记录）。
     c. **正确证据是全量 diff**：把本地文件**去掉本次新增的条目**后与生产版整体 `diff`，
        逐行确认**每一处差异的方向都是「本地更新」**、**没有任何一处是生产独有的实质内容**，才允许进入覆盖。
        构造对照文件：`{ sed -n '1,<头部行数>p' 本地 ; sed -n '<首条旧条目行号>,$p' 本地 ; } > /tmp/local_minus_new.md`
        —— 切之前必须先 `sed -n` 打印该行号确认切点正确，**不许凭行号硬切**。
     d. **禁止省略 diff 输出**：省一行就等于这次判断作废。
     e. **diff 的判读判据（2026-08-21 同日第二次踩到，必读）**：**绝不许用「是否出现 `<` 行」当判据。**
        `diff` 的 `c`（替换）型 hunk **必然**带 `<` 行——那是被替换掉的旧行，不是生产独有内容。
        只有**没有对应 `>` 行的 `<` 行**（`d` 型 hunk，或 `c` 型里本地丢了信息）才算生产独有内容。
        正确判据只有一句：**逐行确认每一处差异的方向都是「本地更新」、没有任何一处是生产独有的实质内容。**
        实例：2026-08-21 context 同步单把验收判据写成「不得出现任何以 `<` 开头的实质内容行」，
        而同一份单子的【背景口径】里明明预告了「§7 conflict 那条改写」——**预告与判据自相矛盾**，
        部署侧照判据停手，闸门全过却白跑一轮。**判据必须与预告同源：预告了改写，判据就必须容得下 `c` 型 hunk。**
     - **闸门 B-2 · 尾部 md5 强证明（适用时优先用，比数条目强）**：当本地相对生产是**纯前置追加**时，
       用生产文件的字节数去截本地文件末尾，两者 md5 相等即证明「生产内容原封不动是本地的后缀」，正文分叉为 0：
       `PB=$(wc -c < /tmp/prod_TCL.md | tr -d ' ')` 然后比对 `md5 -q /tmp/prod_TCL.md` 与 `tail -c $PB 本地 | md5 -q`。
       **中段有更新时本证明必然不等，此时它「不适用」而非「未通过」**，应改用上面 c 的全量 diff（diff 是更强证据，不是弱化）。
   - 覆盖前逐个备份生产原文件为 `<原名>.bak.YYYYMMDD_HHMMSS`。
   - 传输用 `ssh host "cat > 绝对路径" < 本地绝对路径`；**不要用 scp**（2026-08-14 连续两次 `scp_rc=0` 但远端文件不存在）。
   - ⚠️ **教训（2026-08-14 实测）**：本条此前只写在「context 单写入方制度」里、不在部署步骤中，结果**近两周的部署一次都没同步过** —— 生产 context 落后 63 条 TASK_CHANGE_LOG 条目（AI财务批1~13、SEM 治理、单品现金利润页等全部缺失），`PROJECT_CONTEXT` 停在 8-03。而「context 使用规约」要求每个新任务开工前必读**生产端**这几个文件，等于后来者一直在读已作废的口径。**规则不进必经流程就不会被执行**，故本条固化为编号步骤。

## 3. 关键设施速记

- 生产机 host：`company-ai`；代码根：`/opt/lingxing-auto`。

- 本地仓库根：`/Users/chen/Documents/New project`（Mac）。
- 灰度开关变更（如 `AUTH_ENABLED`）：改 `.env` 后需重启才生效；高风险开关（会挡全站/挡登录的）务必"先验证再开启"，最后一步才开。

## 3.5 交付即出「可粘贴部署提示词」（强制模板，别再靠记忆）

> 教训：多次只给散文说明，需求方还得自己翻译成部署指令。**每次交付必须直接产出下面这段可整段复制给部署 AI 的提示词**，字段一个不少。

必含字段：
1. 任务标题 +（若已提交）本地 commit 短号。
2. 角色声明：部署 AI 从 Mac 仓库按白名单逐文件 scp 到 `company-ai:/opt/lingxing-auto`，禁整目录 rsync / git pull；后端/cron 是否改动写清。
3. 交付清单，每个文件一行，标 **新增 / 覆盖**；覆盖的给 `基线SHA8 -> 目标SHA8` 与 `md5`；新增的给 `md5`。
4. 步骤：对账(覆盖文件 md5 local↔线上，不符先回拉) → 备份线上被覆盖文件 → 白名单 scp（列全路径）→ `tsc --noEmit` → 前端 `npm run build`（改了 admin-frontend 时，记 bundle 名）→ SQL（**写账号**，幂等/不删历史）→ 需要时重启 `lingxing-admin.service` → 只读冒烟（`curl /admin/` 期望 302）→ **context 镜像同步（§2.2 第 9 步，必填，缺此项视为交付未完成）**。
5. 验收标准：SQL 验收 SELECT 期望、build 0 报错 + bundle 名、curl 码；登录态点选项注明由代码侧浏览器复验。

产出即算交付物的一部分；缺这段视为交付未完成。

## 4. 高风险变更的通用护栏

- 任何"会把人挡在外面"的开关（全站登录网关、fail-closed 鉴权）：**先在开关关闭状态下验证核心账号能进，最后一步才开开关**。
- 变更配套：测试命令 + 验收标准；覆盖文件配套备份；SQL 配套主键/唯一键核对。

## 3.6 部署提示词的排版格式（强制，2026-08-02 固化；§3.5 管"字段一个不少"，本节管"长什么样"）

> 教训：代码AI多次凭记忆自创格式（编号列表式、"【部署 | xxx】标题+横线"式），需求方已两次纠正并给出截图样例。**给部署AI的提示词必须是一整段可直接复制的文字，用【】分节，开头永远是【角色】。**

模板（节名与顺序固定；不适用的节可整节省略，但不得改名、不得换序）：

```
【角色】你是部署AI，在生产 /opt/lingxing-auto 干活。本任务=<纯只读探测 / 代码上线 / 建表+上线>。<读写边界写死，例："全程只允许 SELECT，禁止 INSERT/UPDATE/DELETE/DDL、禁止写库、禁止改任何现有文件与定时任务">；连接从环境变量读、禁止硬编码/打印密钥。

【背景口径（现网，勿改）】
- <本任务涉及的表/接口/已知基线数值，逐条列出；部署AI不得自行改口径>

【文件】（涉及文件同步时才有此节）
- 新增/覆盖：<路径> md5=<值>；覆盖的写"基线SHA8->目标SHA8"并先备份线上原文件；从 Mac 仓库白名单 scp，禁整目录 rsync / git pull；标注源 Mac HEAD 短号

【步骤】
1. <逐条可直接执行的命令，写全路径；对账→备份→scp→tsc→build→SQL→重启→冒烟，按§2.2顺序，不适用的写明跳过或直接省略>

【验收】
- <期望输出/已知报错基线/服务不受影响的判据>

【回传】
- <要求贴回的完整输出段落，明确哪几段不许截断>
```

硬性要求：
1. 一份整段，且必须放在一个代码块（``` 围栏）里发出——聊天界面只有代码块才带一键复制按钮（见需求方截图红箭头），当普通正文发出=需求方无法一键复制=错。不拆多条消息、不加模板外的开场白/结尾。因此提示词正文内部不得再嵌套 ``` 围栏（命令直接写行内，或用缩进），否则外层代码块会被截断。
2. 开头必须是【角色】，且写明本任务读写边界（只读探针必须写"全程只允许 SELECT/只读接口调用"）。
3. §3.5 的必含字段（角色声明、新增/覆盖标注、md5、对账备份、验收标准）全部融进上述【】节内，一个不少。
4. 输出部署提示词前，先回看本节模板，禁止凭记忆输出。

## 部署提示词交付方式（2026-08-03 需求方定稿；废止旧「文件+指针」约定）

**唯一正确方式：提示词一律【内联】发在对话里，整段放进一个代码块（``` 围栏），供需求方右上角一键复制。** 聊天界面只有代码块才带 Copy 按钮（需求方已多次用红箭头截图指出）。排版严格照 §3.6：开头 `【角色】`、`【】` 分节、正文内**不得**再嵌 ``` 围栏（命令写行内或缩进），否则外层代码块被截断。

- 交付前一行给一句极短说明（例：`给部署AI的提示词（整段可一键复制）:`），紧接着就是那个代码块，别加多余开场白/结尾。

## nginx 代理坑：新增 /api 路由必须落在已代理前缀下（2026-08-03 教训）

生产前端在 `http://42.193.254.170/admin/`（nginx :80），nginx **按前缀**代理到后端 :3001，**不是** blanket `/api/`。实测：`/api/pmc/*` 全代理（含不存在子路径返回后端JSON 404），但 `/api/pmc-inventory/` **未代理** → 浏览器拿到 nginx 的 404 HTML → 前端报 `Unexpected token '<', "<html>..."`。而 `curl localhost:3001` 直连后端一切正常，极易误判"后端没问题就没事"。

规则：
1. **新增后端 /api 路由，挂载路径必须落在 nginx 已代理的前缀下**（如 `/api/pmc/xxx`、`/api/feishu-raw-sales/xxx`），不要新造顶层前缀（如 `/api/pmc-inventory`），否则要改 nginx。
2. 验证接口**必须走公网 nginx 地址**（`http://42.193.254.170/api/...` 或 `/admin/api/...`），不能只 `curl localhost:3001`——两者代理路径不同。
3. 前端报 `Unexpected token '<'` = 接口返回了 HTML（多为 nginx 404），优先查"该路径 nginx 是否代理"。
4. 案例：库存一览表接口从 `/api/pmc-inventory/overview` 改为 `/api/pmc/inventory/overview` 后即通（复用现有 /api/pmc/ 代理，不动 nginx）。

## 3.8 铁律：退出码为 0 不等于目标状态达成（2026-08-14 需求方定稿，长期有效）

> 一天之内同一类故障出现三次，全部是「命令报成功、事情其实没做成」：
> ①`mysqldump` 写出 **0 字节**备份，却因验收看的是 `ls` 的退出码而被判为备份成功；
> ②`scp` 返回 `scp_rc=0`，远端文件根本不存在（连续两次）；
> ③（历史·§帮助文案节）`UPDATE` 实际已写入，但含全角字符的 `LIKE` 验证返回 ok=0，被误判为未写入。
> 共同根因：**把「命令执行完了」当成「目标状态达成了」**。

**通则：验收必须断言目标状态本身，不得以命令退出码作为结论。**
退出码只能用来决定「要不要继续」，不能用来回答「做成了没有」。

### 3.8.1 文件上传：`scp 成功 ≠ 部署成功`

任何文件推送（`scp` / `rsync` / 流式重定向）后，**必须**依次断言：

1. 本地 hash（`md5sum`，记入交付清单）
2. 上传动作执行
3. **远端文件存在**（`ls -la` 命中）
4. **远端 hash 与本地 SAME**（逐字比对，不看命令退出码）
5. **大小 / 行数合理**（`wc -c` / `wc -l` 与本地一致）

五项全过才允许进入下一步。**禁止以 `scp_rc=0` 作为落地依据。**

`scp` 异常时的兜底：`ssh host "cat > /目标/绝对路径" < "/本地/绝对路径"`。
这是纯文件流，**不属于**本文档禁止的 `ssh host "echo <base64> | ..."` 内联模式（后者因外层引号解析吃字符而被禁）。兜底成功后仍须走上述五项验收。

### 3.8.2 数据库备份：`mysqldump rc=0 ≠ 备份成功`

必须同时满足，缺一即判为备份失败：

1. 文件存在
2. **size > 0**（`wc -c`）
3. **内容能识别到目标对象**（`grep -c 'CREATE TABLE.*<表名>'` 命中 ≥ 1）

配套禁令：

- `mysqldump` 命令**一律不得写 `2>/dev/null`**——吞掉 stderr 正是 0 字节备份被误判的直接原因。
- 验收必须取 **`mysqldump` 自身的退出码**，不得用其后 `ls` / `echo` 的退出码代替。
- `mysqldump` 一律加 `--no-tablespaces`（无 PROCESS 权限时 tablespace 段报错易被误判为备份失败）。
- **被判为无效的备份文件必须在 TASK_CHANGE_LOG 明确标注「不可作为恢复点」**，仅保留作教训物证；禁止因为「目录里有个同名文件」就认为存在可回滚点。

### 3.8.3 通用检查清单（写进每次交付的验收节）

- SQL 写入类：验收查**目标行的实际值**（如唯一的 ASCII `updated_by` 批次标记），不查命令返回。
- DDL 类：验收查 `SHOW CREATE TABLE` / `SHOW INDEX` 的**实际结构**，不查 ALTER 是否报错。
- 服务类：验收查 `systemctl is-active` 与只读冒烟接口，不查 `restart` 的退出码。
- 通报类：验收查测试群**实际收到的消息**，不查发送函数返回。

## 3.9 context 并发写入纪律：只做锚点插入，禁止整文件回写（2026-08-19/20 实测事故后固化）

> 事故实证（2026-08-19 一天内 TASK_CHANGE_LOG 被非本会话内容改动 3 次）：
> ①本会话落档 3747 行后，下一次读取变为 3757 行且**本会话条目被整文件回写抹掉**（靠 head/tail 插入才保住对方条目，否则双向丢失）；
> ②此后又两次在落档间隙被追加（3790→3796、3803→3839）。
> 根因：`context/*.md` 是「读全文 → 内存改 → 写全文」的操作模式，天然**后写赢**；两个写入方间隔几分钟就足以互相抹掉。

### 3.9.1 写入方式（强制）

1. **禁止整文件回写**。改 `TASK_CHANGE_LOG.md` 一律用**锚点式**：新增条目走 `head -n 4` + 新条目 + `tail -n +5` 拼接（保留文件头三行与既有全部条目）；改既有条目走**唯一锚点串替换**，替换前必须 `assert count==1`，命中数≠1 立即停手。
2. **落盘前必须重读当前文件并记录 md5**。距上次读取超过一次工具调用，一律重读；发现行数/ md5 与预期不符 → 先核对自己的条目是否还在（`grep -c` 本批标题），再决定合并策略，**禁止直接覆盖**。
3. **落盘后立即记录新 md5/行数/字节**，作为交付清单与部署单闸门 A 的基线值。

### 3.9.2 闸门 A 基线过期的裁决方法（超集自证，取代「凭记忆判断」）

生产 md5 与部署单基线不符时，**不得凭「看起来像我的旧版」放行，也不得因为不等就判定他人直改**。裁决须用**可计算的证据**，二选一：

- **超集自证（首选）**：在本地把「本会话对该文件所做的全部修改」逐字撤销，若还原结果的 md5 **精确等于生产当前值**，即证明本地新版是生产版的严格超集、零内容丢失 → 放行，并把闸门 A 基线更新为生产当前值。
  实证：2026-08-20 生产 `9081ead0`(3839行) 经撤销本会话两处修改后精确还原，据此放行同步 `78197ca2`(3844行)。
- **无法自证时**：把生产版拉回本地做全文 diff，逐条确认生产独有内容是否已包含在本地版中；有任何一条不在 → 先合并再同步，**绝不覆盖**。

### 3.9.3 闸门 B 的已知盲区：条目改名会被误判为「生产独有」

`comm -23` 比对的是**标题字符串集合**，因此把条目标题从「— 本地完成待部署 / 部署单执行中」改名为「— 已上线✅」时，生产的旧标题必然被判为「生产独有」，**这不是内容丢失**。

- 部署单必须**预先声明**本批允许出现的生产独有标题（逐行列出），并要求部署 AI 对每一行做「能否与本地某条改名后条目一一对应」的判定。
- 能一一对应 → 放行；出现无法对应的第三方标题 → 停手回报，回到 §3.9.2 裁决。
- **禁止**因为这个盲区就放宽闸门 B 为「不比对」——盲区只豁免改名，不豁免缺失。
- ⚠️ **预声明清单必须由实际比对生成，禁止凭记忆写**（2026-08-20 实测：部署单写「本批仅新增条目、未改既有标题」，漏算了**上一批改名但尚未同步**的那条，导致部署 AI 正确停手、白跑一轮）。正确做法：出部署单前先在本地跑一次 §3.9.2 的**超集自证**——撤销本会话对该文件的全部修改（含前几批未同步的改名），若 md5 精确还原为生产当前值，即可据此列出准确的允许清单。
- **跨批次累积**：条目改名与生产同步不一定同批完成，未同步的改名会**累积**到下一批的闸门 B。预声明清单的范围是「生产当前版 → 本地当前版」之间的全部差异，不是「本批新做的改动」。

### 3.9.4 多写入方并存时的最小自保

- 每批交付在 TASK_CHANGE_LOG 落档时，**条目标题必须自带可 grep 的唯一批次特征**（日期 + 模块名），便于事后自证「我的条目还在不在」。
- 部署完成后回改状态（待部署 → 已上线✅）时，同样走唯一锚点替换，**不重写整条**。
- 发现自己的条目已被抹掉：不追责、不回滚他人内容，直接把本批条目按 §3.9.1 重新插入，并在条目内记录一次「曾被覆盖」的事实。

### 3.9.5 sql 编号与帮助文 SQL 的登记纪律（2026-08-20 撞车事故后补）

> 实证：多会话并行各自取号，Mac 侧出现同号不同名——`073_help_ads_fee_report.sql` / `073_help_order_profit_v2_v2.sql`、`074_help_ads_fee_report_v2.sql` / `074_storage_weekly_charge.sql`。
> 同日另查出生产 `sql/` 缺 4 个帮助文 SQL（疑直接 scp 到 `/tmp` 执行后未落档），生产端无法追溯帮助文变更源。

1. **取号前必查**：新建 `sql/` 文件前一律先 `ls sql/ | sort | tail -3`，取最大号 +1；文件名必须带模块特征（`075_help_ads_fee_split.sql` 而非 `075_fix.sql`）。
2. **取号即登记**：交付清单与 TASK_CHANGE_LOG 条目中必须写明本批占用的编号，供其他会话取号时参照。
3. **已执行的撞号文件不改名**：改名会让 TASK_CHANGE_LOG、部署记录与生产执行史之间的追溯断链；只在 log 登记冲突事实即可。
4. **帮助文 SQL 必须落生产 `sql/` 目录留档**：允许 `scp` 到 `/tmp` 执行，但同批必须另传一份到 `/opt/lingxing-auto/sql/`；只在 `/tmp` 执行 = 生产端无源可溯，视为交付未完成。
5. **帮助文 `updated_by` 一律 ASCII 批次标记**（`ai_batch_<日期>_<模块>`），**禁止留 `system` 或空**——否则 §3.7 的验收判据失效，无法回答「这行是哪一批改的」。存量 `system` 值不追改，新批次必须合规。

## 3.10 2026-08-22 事故后新增的七条铁律（一次误覆盖 + 五次判据出错换来的）

> 背景：2026-08-22 运营日志一期第四~六单当天，发生一次**生产功能被误覆盖**（第四单 §10.1 系统运营日志被删，
> 因未重启而线上零影响，已回滚），以及**五次判据写错**。完整经过见 `TASK_CHANGE_LOG.md` 同日「第六单」条目。
> 以下七条是那一天的直接产物，**每一条都对应一次真实翻车，不是预防性条款**。

### 3.10.1 编辑只在仓库进行，禁止「暂存目录」
**根因铁律。** 当天第四、五单的所有 Mac 侧编辑都发生在 `.deploy_tmp_syslog_YYYYMMDD/` 暂存目录，
从那里 scp 到生产，**仓库 `src/` 一次都没被回写**。结果：仓库精确停在当天开工前，
而闸门只盯着生产侧，两者的分叉完全不可见，下一次从仓库发起的部署直接把生产功能覆盖掉。
> **暂存目录让「仓库」与「部署源」变成两个东西，而闸门只盯着其中一个。**
> ⇒ 所有编辑一律在仓库工作副本内进行。确需临时目录时，**用完必须立即回写仓库并三方对账**，
> 否则该目录必须改名加 `_ARCHIVED` 后缀，使其不可能被误当作工作目录。

### 3.10.2 闸门 A 必须两侧
改动票的闸门 A **必须同时给出本地（Mac）与生产两侧的期望 md5**，两侧都要核、任一侧不符即停手。
**缺一侧就是票没写完。** 当天 context 文件每次都做两侧对账、代码文件一次都没做，事故正出在代码文件上。

### 3.10.3 「md5 变了」不等于「基线对」
推送前除确认本地 md5 已变（证明编辑落盘）之外，**还必须确认本地文件是从当前生产版本演化来的**。
md5 变了只说明动过，不说明改在了正确的基线上。

### 3.10.4 锚点不匹配一律停手，禁止自行对齐
执行侧遇到「锚点与文件实际内容不匹配」时，**唯一合法处置是停手回报**。
禁止近似匹配、禁止「按真实文件对齐、实现相同语义」的现场改写。
锚点由代码侧给出，对不上意味着**票或基线有错**，必须回到代码侧裁决。
当天丢失的 §10.1，很可能正是在一次「自行对齐」中被删的。

### 3.10.5 判据只能是 diff 逐处核对 + typecheck
**grep 计数永远只是线索，不是判据。** 当天五次判据出错全部源于此：
- 中文注释会命中同名关键字（预告 grep=2，实际 4）
- 构建产物里的中文（曾错误归因为 esbuild 转义，被对照组当场推翻）
- 新写的代码自己带了该关键字（预告 `sys_ops_log`=3，实际 4）
- 日志文件 0 字节被当成「任务没跑过」（实测表里有三万行数据）
- 把一张**运营正在写的活表**的计数当静态基线（三小时里涨了 30 条）
> 判据只有一句：**逐处确认每一处 diff 都对应本票预告过的改动，且没有任何一处是未预告的内容**，外加 typecheck 通过。
> 涉及"未被破坏"的证明，用**超集自证**或"目标片段未出现在 diff 中"，不要用计数。

### 3.10.6 不预测 hunk 数量
同一处逻辑改动会被 `diff` 按公共行切成多段（当天一次 `main` 重构被切成 4 段，预告 7 处实际 10 处）。
**预告改动的「处」，不预告 diff 的「hunk 数」。** 判据是每处差异都对应预告，不是数量相等。

### 3.10.7 SQL 与代码的写入通道
- **SQL 一律 heredoc，禁用 `mysql -e` 带字符串字面量。** 当天实测：同一张表，`-e` 形式返回了
  不存在的列、不存在的规则名、不存在的日期，与 heredoc 直查互相矛盾。
- **远程 SQL 一律 `ssh host bash -s` + heredoc**，不要用 `ssh host '…heredoc…'`——
  单引号包裹会把 SQL 里的字符串字面量转成字面文本（当天实测 marker 输出成 `"'=== … ==='"`）。
  每票带一句引号自检：`SELECT 'quote_ok' AS literal_test;`，输出必须无多余引号。
- **代码写入只用文件编辑工具**，禁止用 shell/python heredoc 写 TS/TSX——
  `{ } ? : </span>` 会被 bash 解析破坏（当天实测直接失败）。
- **`ssh -n` 与「喂 stdin」互斥（2026-08-24 两次实测）**：`-n` 禁读 stdin，与 `bash -s <<'EOF'` heredoc
  或 `ssh host "cat > 路径" < 本地文件 同用时，脚本/文件内容被整个吞掉——远端拿到空输入、
  **零输出、零报错、退出码 0**（典型「命令成功、事情没做成」，§3.8 同族）。
  规矩：喂 stdin 的调用（heredoc SQL、cat> 流式传输）**一律不加 `-n`**；
  反向坑同日也踩过：循环体内的单命令 ssh **必须加 `-n`**，否则 ssh 默认转发本地 stdin，
  会把 while read 的剩余清单行吞掉（实测差异清单 4 行只处理了 1 行）。
  一句话：**读 stdin 的不加 -n，不读 stdin 的必加 -n。**

## 3.11 部署侧合规审查：部署AI 是代码AI 的最后一道闸门（2026-08-22 需求方立规，长期有效）

> **立规背景**：§3.10 的七条铁律解决的是「怎么做对」，但全部依赖代码侧自觉。
> 2026-08-22 的误覆盖事故证明：**代码侧的自检可以整体失效而无人察觉**——票上闸门A 只写了生产侧、
> 判据用 grep 计数、编辑发生在暂存目录，三项全错，而部署侧当时并没有「必须审查代码侧是否守规」的授权与清单。
> 那次没造成损失，靠的是部署侧临场发现 diff 异常并自行停手，**属于个人判断，不是制度**。本节把它变成制度。

### 3.11.0 授权与地位（先把权力关系写死）

1. **部署AI 对代码AI 的交付物有独立审查权与一票否决权。** 任一检查项不通过 → **停止部署**：不推送、不建表、不重启、不发通报。
2. **默认 fail-closed**：检查项「无法判定」等同于「不通过」。证据不足不得放行。
3. **部署AI 的停手只有需求方能推翻，代码AI 不能。** 代码侧提供的任何补充说明只能作为证据提交，不能作为放行理由；两侧禁止就同一张票私下往返修补超过一轮，第二轮仍不通过即上交需求方裁决。
   - **唯一例外（2026-08-22 需求方批准）**：仅 **A 组格式类问题**（A1 排版、A2 缺字段、A5 单票单任务）允许代码侧改完重开票，不惊动需求方。
   - 例外的边界写死：**B 组、C 组、以及 A4 越权扫描一律不适用例外**——那三类涉及基线、生产状态与授权，必须上交。
   - **每次动用例外，部署侧必须在审查回执里单独记一行 `EXCEPTION_USED: A<n>`**（§3.11.7-2）。同一张票动用例外**超过一次**，或例外后重开的票再次 FAIL，一律上交需求方，不得继续内部循环。
   - 例外只免「打扰」，不免「留痕」：用没用过例外、用了几次，必须可被 `grep EXCEPTION_USED` 查出来。
4. **「代码AI 说已自检通过」不构成证据。** 部署侧必须自己跑出判据。本节所有检查项由部署侧亲自执行并逐条回传判定结果，**回传缺任何一条 = 本单验收不通过**。
5. **禁止代劳补票**：部署侧发现票缺字段、缺 md5、缺锚点、缺验收标准时，**不得自行补齐后继续执行**，一律退回代码侧重开票。

### 3.11.1 A 组·收单闸门（只看票本身，先不碰生产）

| # | 检查项 | 判据 | 不通过 |
|---|---|---|---|
| A1 | 格式合规 | 整段单代码块、开头 `【角色】`、`【】` 分节且顺序符合 §3.6 | 拒单 |
| A2 | 必含字段齐全（§3.5） | 任务标题 / 角色声明 / 逐文件「新增 或 覆盖」标注 / **两侧 md5（§3.10.2）** / 对账+备份步骤 / 验收标准 / **context 镜像同步步骤（§2.2-9）** | 拒单 |
| A3 | 读写边界写死 | 票头明示本单为 纯只读探测 / 代码上线 / 建表+上线，并写明禁止动作 | 拒单 |
| A4 | 越权动作扫描 | 票中不得出现 §3.11.4 黑名单动作，除非票内**逐字引用**需求方授权原话 | 拒单 |

### 3.11.2 B 组·站前对账（碰生产，全程只读）

| # | 检查项 | 判据 | 不通过 |
|---|---|---|---|
| B1 | 闸门A 两侧 md5（§3.10.2） | Mac 实测 md5 == 票上 Mac 基线，**且** 生产实测 md5 == 票上生产基线。两侧都要核 | 停手 |
| B2 | 基线演化性（§3.10.3） | 本地新版必须由**当前生产版**演化而来。纯增量用 §3.9.2 超集自证；有中段修改用全量 diff 逐处确认方向均为「本地更新」 | 停手 |
| B3 | 锚点命中数（§3.10.4） | 票上每个锚点在目标文件中 `count == 票上声明值`（默认 1）。≠ 即停手，**禁止近似匹配、禁止自行对齐改写** | 停手 |

| B7 | 分层与写入方合规 | 改动不得让 AI 层直写 DIM/FACT/BIZ/EVENT；不得让前端或 GPT 新增直查 RAW；不得为已登记表引入第二写入方（DATABASE_MAP §表↔唯一写入方映射） | 停手 |

**B6 补充 · 通报确认的取证方式（2026-08-22 需求方定）**

代码侧写在票里的「已确认」是自己给自己开证明，**不算数**。合法证据只有两种，二选一：

1. **需求方在票外单独回一句确认**（聊天里直接对部署AI 说，或转发给部署AI），内容须含：测试群收到、标题与内容正确、未误发生产目标、无异常重复——即 PROJECT_CONTEXT「人工实收门禁」四项。
2. 需求方把确认原话写进 `_deploy_tmp/audit/<日期>_<模块>_notify_ack.txt`，部署侧读文件取证。

两种都没有 → B6 判 FAIL、停手。**部署侧不得代需求方判断"看起来已经测过了"。**

### 3.11.3 C 组·推送后验收（判据只能是 diff + typecheck，§3.10.5）

1. **diff 逐处核对**：每一处差异都必须对应票上预告过的改动，且**没有任何一处未预告的内容**。出现未预告内容 → 立即停手，**不执行 typecheck、不重启、不验收**。
2. **未预告删除检测**：证明「不该动的没被动」，用**超集自证**或「目标片段未出现在 diff 中」。**禁用 grep 计数作判据**（§3.10.5，已五次出错）。
3. **不预测 hunk 数量**（§3.10.6）：判据是「每处差异都对应预告」，不是数量相等。
4. **typecheck 0 错**；目标文件 md5 == 票上目标值；五项落地验收全过（§3.8.1）。
5. **重启是最后一步**，且只在 1–4 全过后执行。§3.10 事故当天线上零影响，唯一原因就是**服务从未重启**。
6. **查询类改动加耗时断言**（2026-08-25 双页面超时事故后新增）：凡改动页面/接口查询路径（换表、换视图、包子查询、改 WHERE/JOIN）的单，冒烟必须含 `time curl` 实测，页面主查询 **<5 秒**为硬判据；超时=验收不通过（细则 §3.11.8）。非查询类改动记 N-A。

### 3.11.4 越权动作黑名单（票中出现即拒单，除非逐字引用需求方授权）

1. 改 `crontab` / `systemd` / `nginx`，而票头未把它声明为本单目标。
2. `DELETE` / `DROP` / `TRUNCATE` / 不带 `WHERE` 的 `UPDATE` / 清空数据表。
3. 整目录 `rsync`、生产 `git pull` / `git checkout` / `git reset`。
4. 覆盖 DATABASE_MAP 登记的人工列，或为已登记表引入第二写入方。
5. 前端或 GPT 新增直查 RAW；AI 层直接写 DIM / FACT / BIZ / EVENT。
6. 飞书真实发送而无测试群确认记录。
7. **从任何暂存目录取源推送**（§3.10.1 根因铁律）——详见下方「第 7 条细则」。
8. 硬编码密钥；验收输出打印 Token / 密码 / Cookie / `Authorization` / `.env` 明文值。
9. 建表无唯一键，或唯一键含可空列（PROJECT_CONTEXT §5.1）。
10. 部署侧自行修改代码、自行「修正类型错误」（§1.7）。

**第 7 条细则 · 区分「取源」与「放产物」（2026-08-22 需求方定）**

暂存目录本身不是禁忌，**把它当部署源**才是。判据是**数据流向**，不是目录名：

| 方向 | 定义 | 是否允许 |
|---|---|---|
| **取源** | 从该目录**读出**文件 → 推送到生产，或**覆盖回**仓库 `src/` | ❌ **禁止**，无例外 |
| **放产物** | 只读采集结果、审查回执、部署提示词存档、诊断输出**写入**该目录 | ✅ **允许**，且 §3.11.7 要求必须落这里 |

- **部署源永远只有一个：Mac 仓库工作副本**（`src/`、`admin-frontend/src/`、`sql/`、`context/`）。任何 `scp` / `cat >` 的**来源路径**若落在 `_deploy_tmp*`、`.deploy_tmp*`、`_ai_patches`、`_bak`、`tmp`、`.tmp*` 之下 → 立即拒单。
- **编辑一律在仓库工作副本内进行**（§3.10.1）。需要临时目录时，用完必须立即回写仓库并三方对账；未回写的临时目录必须改名加 `_ARCHIVED` 后缀。
- `_deploy_tmp/` 现有用途（提示词存档、只读探测产出、审查回执）**全部属于「放产物」，继续使用**。
- `.deploy_tmp_syslog_20260822_ARCHIVED/` 已按此规则改名封存，**只作历史证据，禁止再从中取源**。
- 判定方法：看命令里该路径出现在 `scp`／重定向的**左边（来源）还是右边（目标）**。左边=取源=拒单；右边=放产物=放行。

### 3.11.5 停手后的标准动作（不许自由发挥）

1. **立即停在当前步**，不执行后续任何一步。
2. 若文件已推送但**未重启**：用本单备份回滚到推送前版本，并断言回滚后 md5 == 推送前基线（§3.8.1 五项）。**不重启即线上零影响。**
3. 若已重启且已确认异常：先只读诊断，**不盲目回滚**（§2.2-8）；把服务状态与只读冒烟结果一并回传。
4. 完整回传：命中的检查项编号、判据原始输出（diff / md5 / 报错，**不许截断**）、生产当前状态、已执行到第几步。
5. 交需求方裁决。同一张票第二次仍不通过，**不得再由两个 AI 之间协商解决**。
6. 事后由代码侧把该次拦截写入 `TASK_CHANGE_LOG.md`（条目标题带日期与模块，便于 grep 自证），并判断是否需要新增铁律。

### 3.11.6 回传模板（每单必附，缺项即验收不通过）

    A组 A1..A5：逐条 PASS/FAIL（FAIL 附票中原文）
    B组 B1..B7：逐条 PASS/FAIL/N-A（N-A 必须说明为何不适用）
    C组 C1..C6：逐条 PASS/FAIL/N-A（C1 附 diff 逐处对应关系；C6 耗时断言附 time curl 原始输出，非查询类改动写 N-A）
    EXCEPTION_USED：A<n>，或「无」
    黑名单扫描：命中项编号，或「无命中」
    最终裁定：放行 / 停手（停手须写明停在第几步、生产当前状态、是否已回滚）

**豁免（2026-08-22 需求方定）**：**票头声明为「纯只读探测」的单，豁免 C 组**（无推送、无 diff、无重启，C 组无物可填），回执 C 组统一写 `N-A(只读探测)`。
A 组、B 组、EXCEPTION_USED、黑名单扫描、最终裁定 **五项一项都不能少**——只读探测同样可能越权（例如票里混进 `UPDATE`、或从暂存目录取源），A4 与黑名单扫描恰恰是只读单最需要的两项。

### 3.11.7 防两侧同时失守：需求方的独立自查权（2026-08-22 需求方立规）

> **需求方原问**：「如何避免部署AI 和代码AI 都不遵守规矩？」
> **答案不是再加一个 AI 去监督**——那只是把同一个问题往后推一层。
> 唯一可靠的是：**让违规必然在客观介质上留痕，并且需求方能在不询问任何 AI 的前提下独立查出来。**
> 本节的重点从「防止违规」转为「**违规必被发现**」。

#### 3.11.7-1 原则

1. **AI 的自述一律不作为证据。** 聊天里的「已核对」「已通过」「已同步」全部只是声明。
2. **证据必须是机器产物原文**：`md5sum` / `diff` / `tsc` / `SELECT` 的原始输出，**禁止用结论代替原文**。回执里只写 PASS/FAIL 而无原始输出的，视为**回执无效**，等同该项 FAIL。
3. **证据必须落文件，不能只落聊天。** 聊天会滚走、会被截断、无法被下一个会话 diff；文件可以。

#### 3.11.7-2 每单必须落在 Mac 仓库的三份物证

| 物证 | 路径 | 由谁写 | 时机 |
|---|---|---|---|
| 票原文 | `_deploy_tmp/tickets/<日期>_<模块>.txt` | 代码侧 | 出票时 |
| 审查回执 | `_deploy_tmp/audit/<日期>_<模块>_audit.txt` | 部署侧 | 执行后（含 §3.11.6 模板 + 机器产物原文 + `EXCEPTION_USED`） |
| 部署台账 | `context/DEPLOY_LEDGER.md` 追加一行 | 部署侧 | 放行并重启后 |

台账每行固定字段：`日期 | 模块 | 文件 | Mac_md5 | 生产目标_md5 | 是否重启 | 回执路径`。
**台账只追加，不改写历史行**（同 §3.9.1 锚点纪律）。
**「文件」列必须逐个写完整仓库相对路径（多文件用 + 分隔）**——一致性哨兵按完整路径/完整文件名
做全文匹配来豁免已登记改动，简写（如 `sql/015`）必然被误报为「台账查无」（2026-08-24 哨兵首跑实证，
5 项误报全部源于此）；已写成简写的历史行不改写，追加补登行豁免。

#### 3.11.7-3 根机制：需求方一条命令自查（不经任何 AI）

在 **Mac** 上执行：`bash scripts/code_sync_check.sh`，结果在 `/tmp/code_sync_check.log`。该脚本纯只读、纯本地发起，**不依赖任何 AI 的自述**。

判读（任一非空即为异常信号）：

| 输出段 | 非空说明 |
|---|---|
| 内容不一致 | 有改动没同步，**或有人绕过了流程** |
| 仅线上有 | **生产被直接改过**（违反「生产不是真源写入方」） |
| 仅本地有 | 有待部署改动，或部署漏推 |
| `._` 垃圾文件 | **发生过整目录/通配 scp**（违反 §1.2 / §1.3） |

**交叉判据（关键）**：把上述异常项与 `context/DEPLOY_LEDGER.md` 比对——
**异常文件在台账里查无对应记录 = 这次改动没走流程**，无论两个 AI 当时怎么回报。
生产文件的 md5 是客观事实、任何时候都能重算，因此**台账是不可抵赖的**：
生产当前 md5 ≠ 台账最后一条目标 md5 → 中间必有一次未登记的改动。

#### 3.11.7-4 定期独立巡检

- **每周至少一次全量对账**，范围四目录：`src/`、`admin-frontend/src/`、**`sql/`**、**`context/`**，外加 `crontab -l` 行数、`systemctl is-active` 服务清单。
- **必须由第三方只读会话执行**——不得由当周经手该改动的代码AI 或部署AI 自查。自己查自己不构成监督。
- 巡检结果落 `_deploy_tmp/audit/weekly_<日期>_sync_audit.txt`，异常项直接上报需求方。

#### 3.11.7-5 兜底：当两侧都失守时会发生什么

即使代码侧与部署侧同时不守规矩，下列事实**无法被两者掩盖**，需求方随时可独立取得：

1. 生产文件的 **md5** —— 客观、可重算、与台账一比即知。
2. 生产 `crontab -l` 与 `systemctl` 状态 —— 客观运行态。
3. 生产 `logs/` 下的备份文件 `*.bak.YYYYMMDD_HHMMSS` —— 每次覆盖都必须留备份，**没有备份 = 没走流程**。
4. MySQL 表的 `SHOW CREATE TABLE` 与 `updated_by` 批次标记 —— 客观结构与写入痕迹。
5. `._` AppleDouble 文件的存在 —— 整目录推送的物证，删不干净就一直是证据。

**因此制度的落点是：三份物证 + 一条自查命令 + 每周独立巡检。**
规矩管不住铁了心不守规矩的执行方，但物证能保证事后一定查得出是哪一侧、哪一单、哪个文件。

### 3.11.8 查询类改动的性能验收：守恒断言≠可上线（2026-08-25 双页面超时事故后固化）

> 事故：单10/单11 用「三分支UNION+窗口函数」派生视图包住 fact_ads_product_daily（467,403 行）。功能与守恒验收全绿（$454.16 逐分相等），但 MySQL 对含窗口函数的派生表做物化临时表处理，外层 WHERE（日期/店铺/item_id）**不下推**内层 → 每次页面查询先全表扫全量分摊再过滤。SB/SV 页 500（252 秒）、订单利润V2 nginx 超时，需求方开页即撞。单11 回执里「item_id 精确筛约4分钟」已是红灯，被当成"后续优化备注"放行——事故的直接前兆。

1. **凡改动页面/接口查询路径的单（换表、换视图、包子查询、改 WHERE/JOIN），冒烟必须含耗时断言**：`time curl` 实测，页面主查询（默认参数首屏 + 至少一条带筛选参数）**<5 秒**为硬判据。超时 = 验收不通过 = 不得上线；已重启才发现 = 立即回滚，**不留"先上线再优化"**。
2. **数学正确性（守恒/合计相等）与性能是两道独立验收，缺一即 FAIL**。合计逐分相等不能抵扣耗时超标。
3. **派生表/子查询包 ≥10 万行的表，交付前必须先 EXPLAIN**：确认外层条件可下推，或范围/日期窗口已烤入内层；EXPLAIN 预估扫描行数须与"命中数据面"同量级（差一个数量级以上=打回重写）。含窗口函数（SUM OVER / ROW_NUMBER）的派生表**必物化、必不下推**——这类写法只允许出现在范围已在内层限定的视图里。
4. **回执中的耗时异常是红灯不是备注**：任何一步实测耗时超过判据，执行方必须停手回报交需求方裁决，不得写成"遗留优化项"继续放行。
