## 三、核心口径（已拍板并实现）

1. 负责人：`dim_product_owner`(active) → 兜底 `dim_product.owner`（标注来源）→ "未分配"不丢行
2. 公司卡片 = 负责人排行合计（同一份数据求和，天然一致，已验收：销售额 $119,692.49 两边相等）
3. 毛利 = 销售额 −(采购+头程)×销量/汇率 − WFS费×销量 − 佣金 − 广告费；销售额不扣退款
4. 成本：仅 `source_system='lingxing_api'`，三字段分别取非空最新；匹配 store+item+msku → 回退 item+msku；不回退飞书来源
5. 广告：ItemID 级聚合（字段 total_sales），不分摊到 MSKU；有广告无销售 item 也进负责人聚合
6. 佣金：沿用现有店铺规则（12%/15%），platform_fee 仅参考；悦斯CS 固定成本规则保留；汇率/佣金率支持环境变量覆盖（LX_EXCHANGE_RATE 等），默认值与现有生产一致
7. 默认日期 = MAX(stat_date)（当前 2026-07-01），不默认今天/昨天；库存取 ≤date_to 最新快照；库存天数窗口 min(60, 实际数据天数)

## 四、过程中的关键动作（方法论沉淀）

1. **先核查再开发**：SHOW CREATE TABLE 核出多处方案与真实表结构的出入（广告表无 sku、字段叫 total_sales 不叫 ad_sales、日期字段三张表三个名字、fact_profit_daily 字段偏旧），避免了按臆测字段开发。
2. **部署前对账**：md5 对比发现本地与线上 App.tsx/package.json 不一致、线上有 17 个本地没有的文件 → 否决整目录 rsync，改为"线上版回拉对齐 + 白名单 scp 4 个文件"，避免冲掉线上独有改动。
3. **上线前冒烟**：沙盒起完整 adminServer 验证路由挂载（500 而非 404 证明通路），提前定位了"本地 404 是 vite preview 无代理"的环境问题，没有误改代码。
4. **验收数字存疑就复核**：异常数 2/9/5 与早期基准 238/247/403 偏差大，用对比 SQL 定位为旧脚本口径错误（严格 JOIN 遇 msku 空/store_id 空全部失配），证据：当日有广告 item 总数恰为 238。新接口数字正确，文档基准已更正。
