# AI 智能 PMC 提示词 — 漏洞审查清单 v1

审查对象：《AI 智能 PMC 工程师提示词 完整版 v1.0》
审查视角：AI 自动化架构师（保利润 / 防漏单 / 限制工程师自由发挥）
日期：2026-06-21

说明：每条 = 问题 + 影响 + 给工程师的明确修改要求。优先级 P0 必须改，否则系统跑错；P1 会导致漏提醒/重复提醒/数据覆盖；P2 是维护与性能。

---

## P0 · 阻断级（不改会跑错或跑不起来）

### P0-1 cron 时区自相矛盾，可能偏差 8 小时
- 问题：环境表写"系统时区 Asia/Shanghai（北京时间），与服务器时区一致"，但第七节 cron 又按 UTC 配（`0 10 * * 0` 注释为北京周日18:00）。
- 影响：若服务器本地时区确实是北京，按 UTC 配会让任务在 **UTC10:00=北京18:00 的 8 小时偏移后** 触发，即凌晨 2:00 跑，业务时间点全错。
- 修改要求：二选一并写死。
  - 方案A（推荐，服务器=北京时间）：cron 直接用本地时间 `0 18 * * 0`（周日）、`0 16 * * 3`（周三），删掉 UTC 换算。
  - 方案B（服务器=UTC）：保留现有 UTC cron，并在代码内所有时间计算显式用 `Asia/Shanghai`。
  - 验收补充：V10 增加"打印的运行时间戳必须等于北京时间 18:00 / 16:00（±2 分钟）"。

### P0-2 "到仓逾期"缺"到仓日期"字段，规则无法计算
- 问题：R004（到仓超5天未发货，每3天提醒）和 R007（到仓未发货升级超10天）都要算"到仓后第几天"，但领星字段映射表里**没有到仓/入库时间字段**，只有 `quantity_entry`（已入库数量，状态量）。
- 影响：`daysOverdue` 在到仓阶段无基准日期，checkStatus 的到仓逾期分支和升级判断**写不出来**，工程师只能瞎猜或硬编码。
- 修改要求：补一个明确的到仓基准日期来源，按可得性排序：
  1. 优先：确认领星采购单/收货明细接口是否有 `receive_time` / `arrive_time` / 入库时间字段，若有则补进字段表并指明取该字段。
  2. 兜底：以"PMC 通知日志中该 ItemID 首次出现'到仓待发货'阶段的 notify_time"作为到仓基准日期，写进 6.4 逻辑。
  - 二选一必须在提示词里定死，禁止工程师自定义。

### P0-3 "立即/每天提醒"与"一周只跑2次"调度矛盾
- 问题：R003 到仓待发货=超时0天、间隔1天，6.4 写"货到仓当天立即提醒"；R004 到仓逾期"每3天提醒一次"。但调度只有周日18:00、周三16:00 两个入口。
- 影响：货周一到仓，要等到周三才提醒，"立即/每天"的业务预期落空；"间隔1天/每3天"在两次/周的节奏下根本无法实现。这是利润相关风险（到仓压货发不出去）。
- 修改要求：明确口径，二选一。
  - 方案A（推荐）：到仓/发货类提醒新增每日 cron（如 `0 9 * * *` 北京9点），R003/R004 按天生效；采购审批/到货类保留周日+周三。
  - 方案B：承认两次/周节奏，把 R003 间隔改为"每次运行都提醒直到发货"，并把"立即"措辞改成"下一次运行时提醒"，避免误导。

## P1 · 会导致漏提醒 / 重复提醒 / 数据错乱

### P1-1 唯一键 ItemID 撑不住"一个 ItemID 多采购单 / 多 SKU / 多仓"
- 问题：台账规定一个 ItemID 一行，当前阶段更新该行。但同一 ItemID 可能同时存在多张采购单（多次补货、不同仓库），各单阶段不同（一张待下单、一张已到货）。
- 影响：多张单状态写进同一行会**互相覆盖**，只剩最后一张，其余采购单漏跟进、漏提醒。
- 修改要求：改唯一键为 `ItemID + order_sn`（一行=一 ItemID 一采购单），或在提示词中明确"同 ItemID 多单时如何聚合/取哪张为准"。同时定义 SKU→ItemID 是否一对一，多 SKU 映射同一 ItemID 时明细如何归并。

### P1-2 按"行号"写入易错位，可能覆盖人工 I 列
- 问题：6.3/6.5 用"ItemID→行号 Map"后按行号写 cells。
- 影响：飞书表被人工插入/删除行后行号漂移，会写错行、覆盖人工"I 列备注"（V03 直接挂）。
- 修改要求：每次运行**实时按 A 列 ItemID 重新定位行号**再写，禁止跨运行缓存行号；写前再校验该行 A 列值==目标 ItemID，不符则跳过并记日志。

### P1-3 时间字符串解析时区未定，7 天边界差 1 天
- 问题：`auditor_time`/`order_time`/`expect_arrive_time` 算"距今 X 天"，但未规定解析时区。
- 影响：直接 `new Date(字符串)` 按 UTC/本地解析会有 8 小时偏差，恰好卡在 7/14/21 天边界的任务会**早一天或晚一天**提醒/升级。
- 修改要求：统一规定"领星返回时间一律按 Asia/Shanghai 解析，'距今天数'= 按北京时间日期差（向下取整到天）"，并在 config 或工具函数里集中实现，禁止各文件各写。

### P1-4 防重复依赖 stage 文本匹配，枚举不统一会失效
- 问题：防重复靠"同 ItemID + 同 task_stage + 间隔天数"判断，但 checkStatus 产出的 stage 与日志 task_stage 是自由文本。
- 影响：两处措辞不一致（如"到仓待发货" vs "到仓发货"）→ 判重失效 → 重复轰炸或漏发。升级通知若不单独记 stage，会每次运行都重复 @ 江梓博。
- 修改要求：定义一个固定枚举常量（如 `APPROVE_PENDING / ORDER_PENDING_ARRIVAL / ARRIVED_PENDING_SHIP / OVERDUE_SHIP / ESCALATE_*`），checkStatus 和日志 task_stage **必须用同一枚举**；升级通知用独立 `ESCALATE_*` stage 单独防重复。

### P1-5 部分入库未定义
- 问题："quantity_entry=0=未到货，>0=到仓待发货"，没定义 `0 < entry < quantity_real`（部分入库）和多 SKU 采购单部分到货。
- 影响：部分到货可能被误判为"全部到仓"提前提醒发货，或漏判。
- 修改要求：明确口径，例如"`entry >= real` 才算到仓待发货；`0<entry<real` 标记'部分到货'单独一类提醒（或暂不提醒），多 SKU 单按明细逐条判断"。

### P1-6 任务无"终态/关闭"逻辑，已完成任务会被反复扫描
- 问题：全文没有"任务完成后如何关闭"。采购单已发货完成后，台账该行状态如何置终态、是否停止提醒，未定义。
- 影响：已完成任务持续被 checkStatus 扫描，可能误提醒，台账越积越大。
- 修改要求：定义终态（如领星状态=已发货/已完结时，F 列置"已完成"，checkStatus 跳过终态行不再提醒）。

### P1-7 open_id 三处来源，冲突优先级未定
- 问题：固定负责人 open_id 同时出现在 ①6.1 config.ts 硬编码、②config/ownerOpenIds.json、③负责人配置表(3waBiS)。
- 影响：三处不一致时以谁为准未定，改一处其它没改会发错人。
- 修改要求：定死单一数据源（推荐：固定角色读负责人配置表 3waBiS，运营负责人读 ownerOpenIds.json），删除 config.ts 里的硬编码 open_id 示例，避免误用。

### P1-8 "店铺"(B列) 字段无数据来源
- 问题：台账 B 列=店铺，业务跨亚马逊+沃尔玛，但采购单返回字段映射里没有店铺字段。
- 影响：B 列填不出来或留空。
- 修改要求：指明店铺来源（领星采购单是否有 store/seller 字段？或从 ItemID 负责人表带出？），写进字段映射。

### P1-9 时间空值口径不全
- 问题：只说"空字符串=未审批/未下单"。
- 影响：领星实际可能返回 `null` / `'0000-00-00 00:00:00'` / `undefined`，未覆盖会误判已审批。
- 修改要求：统一判定"未发生 = 值为空串 / null / undefined / '0000-00-00 00:00:00' 之一"。

## P2 · 维护性与性能

- **P2-1 通知日志无限增长**：防重复每次全表读飞书日志，时间久了慢且触发飞书 API 限流。要求加"只读近 N 天日志"或定期归档。
- **P2-2 领星 API 无限流/退避**：全量分页 length=100 循环，未提 QPS 限制与重试退避；V01"5分钟内"未限定采购单总量。要求补"分页间隔+失败指数退避重试"，V01 注明测试数据量级。
- **P2-3 readOwners 缓存无定义**：异常处理说"用上次缓存映射"，但没说缓存存哪、何时写、有效期。要求明确（如缓存到 `logs/owners-cache.json`，TTL 24h），否则属工程师自由发挥。
- **P2-4 并发无锁**：周日/周三入口+手动触发可能并发写台账（行号漂移、重复追加）。要求加运行锁（如文件锁/lock 文件）。
- **P2-5 runWednesday "周一未处理" 判据缺失**：6.8"识别周一未处理任务"未给判据。要求明确（如"状态未变化 且 I 列为空 视为未处理"）。

## 一句话给老板的风险结论
现在直接交付，工程师大概率能跑通"采购审批→下单→到货"主链路，但 **到仓/发货环节会失灵（P0-2/P0-3）**、**多采购单同 ItemID 会丢单（P1-1）**、**时区边界会偶发早/晚一天（P0-1/P1-3）**。建议先让工程师就上面 P0 三条 + P1-1/P1-2 给出确认口径，再开工。
